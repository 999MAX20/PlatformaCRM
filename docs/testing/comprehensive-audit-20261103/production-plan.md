# Yandex Cloud: условия допуска и порядок доработок

Аудит 04.11.2026, исходный код `0b3348e1` с зафиксированным WIP. Это план
последующей работы, не разрешение на изменения инфраструктуры или deployment.
Yandex Cloud выбран владельцем; регион, тарифы и состав сервисов не согласованы.
Прежние размеры Hoster.kz не используются как критерий достаточности.

## Решение о готовности

Production-допуск не подтверждён. Помимо целевой среды остаются продуктовые
критерии: деньги плана/авансы/зачёты, голосовой D01, ответственный и происхождение
автоматической записи. Локальные тесты подтверждают только свои сценарии;
mock AI, eager tasks и Windows не заменяют реальный канал, worker или Linux.

Предыдущее требование размещения данных в Казахстане не отменено выбором облака.
Нужно согласовать допустимую конфигурацию Yandex Cloud и движение данных через
AI/BSP/audio/storage/backup с этим требованием. Аудит не выбирает регион и не даёт
правового заключения. Это решение блокирует соответствующее размещение, а не
оставшиеся локальные проверки.

## Проверяемая целевая конфигурация

| --- | --- |
| Сборка и Linux | Детерминированный install по lock-файлам в чистом CI; один идентифицированный образ; запуск/UID/read-only и writable volumes; SIGTERM/drain/restart; используемые версии Python/системных библиотек. Windows build не является этой проверкой. |

Локально обнаружена только dev-конфигурация SQLite/loopback Redis/Vite;
авторизованный внешний стенд не установлен. Docker недоступен. В WSL есть Linux,
но нет подготовленных зависимостей Django/Celery/PostgreSQL/Redis/ClamAV и Docker.
Новый стенд не развёртывался, рабочая конфигурация не менялась.

## Порядок исправлений и зависимости

Это единый план по находкам аудита, а не новая очередь, отменяющая roadmap.
Каждый пакет запускается отдельным поручением; существующие закрытия сохраняют
свои границы. Приоритет P1 означает влияние/порядок, а не утверждение об эксплуатации.

1. **Текущие блокеры рабочего сценария (UI01, OPS-Q01, PERF02).** Убрать зависимость
   аварийного fallback от недоступного провайдера. Задать consumers и проверить
   due/retry/restart в реальном worker-профиле. Риск: общий UI и фоновая доставка.
   Приёмка: искусственный crash даёт работающие действия восстановления;
   каждое семейство очередей исполняет работу после перезапуска без дублей.
   Отдельным backend-пакетом устранить повторную дорогую выборку Clients:
   локальный PG-запрос занимает28.6s, все20Clients attempts в двух профилях
   превысили10s deadline. Сохранить права/фильтры/полные итоги, сравнить heavy и
   distributed datasets и планы запросов; облачные ресурсы определять после этого.
2. **Автоматическая запись (CRM-TERMS01, CRM-EVENT01, REQ03).** Сначала закрыть подтверждённое
   принятие изменённой цены/длительности без нового согласования у Business без
   филиалов. Провести автоматический путь через общие
   проверки принятого Record-контракта, сохранив правила AI и разрешённый actor.
   Выбранный ответственный не равен автоматически авторизующему сотруднику.
   Приёмка: current member/default/provenance, запрет чужого tenant/отозванных прав,
   точные предложенные условия, stale slot, replay и rollback; один запуск
   appointment_created и одна настроенная задача, как в ручном контрольном сценарии.
   Риск: запись/AI и повторные доменные эффекты.
3. **Деньги плана (REQ01).** Версии условий и цен → детерминированное округление →
   аванс и зачёт/реверс → остаток/возврат → UI/история/метрики. Сначала решить только
   ещё открытые нулевые базы и новые terminal corrections. Риск высокий: деньги,
   миграции, конкуренция. Приёмка: суммы сходятся, зачёт не создаёт вторую оплату,
   нет double spend/overrefund, concurrent cancel/complete/retry атомарны;
   достижимый сценарий сотрудника и все относящиеся AC09/14 проверены.
4. **D01 (REQ02).** Подтвердить текстовые команды/grounding/current rights,
   затем аудиотранспорт и редактируемую расшифровку с тем же подтверждением.
   Риск: ошибочная команда/данные/стоимость. До audio определить provider,
   retention и доступ. Приёмка RU/KK/смешанной речи, шум, отказ микрофона,
   обрыв/повтор/неизвестный результат; без подтверждения критическая запись не идёт.
5. **Поиск, состояния и доступность (UI02–08 и дополнительные UI-находки).**
   Серверный scoped-поиск задач; честный Clients error; семантика/клавиатура
   shared selector; заголовки, локали и приглашения. Риск shared-компонентов:
   проверить репрезентативных consumers, загрузку/ошибку/пусто/retry/keyboard,
   RU/KK/EN и320/390/desktop, не переписывать всю дизайн-систему.
6. **Проверки и supply chain (UI09/10, SEC-DEP-01).** Устаревшие assertions
   согласовать с утверждённым контрактом; сохранить реальные негативные проверки.
   Пересобрать dev lock с совместимыми исправленными зависимостями и проверить
   tooling/build в чистом CI. Не удалять проверки и не понижать лимиты ради PASS.
7. **Измеренная производительность и целевой release.** Исправлять подтверждённые
   причины PERF01–03: повторные permission projections в очередях, дорогое
   повторное вычисление Clients metadata и недостающие related-загрузки карточки.
   Затем повторить тот же профиль и отрицательные
   permission/tenant случаи. Выполнить Linux/target/restore/alert/каналы и день
   пилота на точном кандидате; только затем отдельное решение о production.
8. **Исторический native и будущий обмен.** Native до reuse: actor-scoped очередь,
   capacity/deep links, актуальный API/Records, device/build/push/store acceptance.
   CRM–Market после пилота: binding/ID/version/revoke/источник денег, парный replay
   и reconciliation; не считать generic IntegrationConnection готовым обменом.

## Оптимизация, рефакторинг и необязательные улучшения

Обоснованный рефакторинг: единая точка доменных проверок автоматической и ручной
записи (конкретный разрыв REQ03); изоляция аварийного UI от обычных provider-dependent
компонентов (UI01); общая семантика selector (UI04). Приёмка — устранение этих
воспроизведений при сохранении permission/lifecycle и поведения consumers.
Размер файла сам по себе не является основанием.

App shell проходит существующий bundle budget; RU/KK chunks превышают только
предупреждение500KiB. Разделение словарей — необязательное улучшение после
измерения cold load на медленном мобильном устройстве, без обещания эффекта заранее.
Root-default image, mutable image tags и migration-in-web-startup — предложения
по hardening/release, а не доказанные удалённые уязвимости. Приёмка определяется
Linux/runtime/provenance и управляемым release-процессом.

CPU/RAM/число replicas по локальному Windows-прогону не назначаются. Для расчёта
нужны объём Business/записей/вложений, одновременные сотрудники, частота AI/каналов,
очереди и целевой SLO. После исправления query regressions измерить steady state,
burst и recovery; отдельно оценить web, worker, PostgreSQL, Redis и AV. Минимальный
тариф или регион в этом аудите не выбирается.

## Внешние данные и решения владельца

- Совместимость выбранного размещения Yandex Cloud с действующим ограничением
  по данным; регион, схема сервисов, домен и разрешённый target для проверки.
- Только незакрытые денежные edge cases и политика audio/provider/retention;
  уже утверждённые решения R01/D01 повторно не запрашиваются.
- Sandbox/BSP/AI receipts и допустимые лимиты реальных/платных проверок.
- Ответственные за release, backup/restore и серьёзные инциденты; сотрудники
  для фактической приёмки двух Business.
- Native candidate/API, Android/iOS устройства/сборочные среды и store/push accounts.
- Managed filesystem permission profile для отдельного Codex Security Deep Scan;
  текущая попытка не стартовала и не дала security-clean результата.

Эти пункты не заменяют найденные исправимые дефекты и не означают, что весь аудит
заблокирован. Точные локальные результаты и ограничения — в итоговом отчёте.
