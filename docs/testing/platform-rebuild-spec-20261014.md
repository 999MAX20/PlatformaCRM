Задача PLATFORM-REBUILD-SPEC-20261014. Срез кода: `293ac49f0d8b00731cc8b71d7848fb31de1d76f5`.
Роль документа: анализ и проектное предложение, с явно отмеченными решениями владельца.
Это завершение этапа спецификации, не реализация и не новый контракт доступа.
Действующие требования: [продукт](../current/product.md), [доступ](../current/access.md),

## 1. Цель и принятые решения

Команда платформы должна быстро находить клинику, понимать её состояние,
помогать с запуском, обрабатывать обращения и видеть подтверждённые сбои.
Главный результат — законченные рабочие сценарии, а не больше разделов меню.

Владелец подтвердил 14.10.2026:

- Спроектировать /platform заново по рабочим сценариям; сначала спецификация.
- Сохранить проверенные механизмы и удалять старое только после рабочей замены.
- Сделать простую внутреннюю очередь поддержки, без внешнего helpdesk.
- Создавать клинику вручную может только `platform_admin`.
- Сотрудники платформы помогают клинике с настройкой в рамках разрешённого доступа.
- Обращения создаёт команда вручную и клиника через кнопку «Поддержка» в CRM.

Остальные новые поля, статусы, маршруты и UX ниже — проектное предложение.
Они не предоставляют новые права до реализации и принятия соответствующего контракта.
Текущий этап не меняет код, данные, рабочие миграции, процессы или интеграции.
Вне объёма: Django /admin, клинические данные, биллинг и списания, маркетинговые
landing/prospects, новая система ролей, управление облаком, Meta/PS Cloud.

## 3. Рабочие сценарии и права

Технические роли остаются `platform_admin` и `platform_manager`.
«Сотрудник поддержки» — рабочая роль человека, не предложение нового enum.
Superuser-поведение учитывать по действующему контракту, не создавать обходы.

| Действие | Администратор платформы | Сотрудник платформы | Пользователь клиники |
| --- | --- | --- | --- |
| Обзор, список клиник, безопасный operational summary | Действующий доступ | Действующий доступ | Нет |
| Создать клинику | Да, решение владельца; MFA и audit | Нет | Существующий самостоятельный signup отдельно |
| Создать обращение | Да, новый сценарий | Да, новый сценарий | Да, из своей CRM; точная видимость ниже |
| Назначить сотрудника, изменить статус, написать внутреннюю заметку | Предлагается | Предлагается | Нет |
| Читать/писать публичную переписку своего обращения | Да | Да | В разрешённой области своей клиники |
| Изменить сущности CRM, выполнить support action | Только по действующим правилам | Только по действующим правилам | По своей CRM-роли |
| Выдать/расширить support grant | Действующий контракт | Без новых полномочий | Действующий контракт владельца |

Текущее право записи `support-actions` ограничено admin, grant и свежим MFA.
Оно не расширяется этим документом. Публичный ответ на обращение — новый
узкий сценарий поддержки; его нельзя реализовать выдачей общего tenant-доступа.
Помощь сотрудника с настройкой означает объяснение и разрешённые действия;
автоматический вход от имени владельца, чтение пациентов и обход grant не разрешены.

Основные завершённые сценарии:

1. Администратор создаёт клинику → владелец принимает приглашение → клиника
   появляется в списке с правдивым состоянием настройки и следующим действием.
2. Сотрудник находит клинику → видит безопасный summary → открывает обращение
   или доступный сценарий помощи → действие получает traceable history.
3. Клиника отправляет обращение → сотрудник принимает его → отвечает →
   при необходимости ждёт клинику → решает вопрос → история остаётся доступна.
4. Сотрудник видит сбой → открывает его источник и затронутую клинику →
   при необходимости связывает обращение → после восстановления видит новый статус.

## 4. Информационная архитектура и UX

Основная навигация: **Обзор / Клиники / Поддержка / Операции**.
Карточка клиники — вложенный рабочий экран, а не ещё один пункт меню.
Интеграции и AI отображаются в контексте клиники и операций.
Настройки и управление сотрудниками не получают пустой раздел «на будущее».
Предлагаемые подписи согласовать с i18n; это функциональная карта, не финальный копирайт.

| Экран | Данные и действия | Пустые/ошибочные состояния |
| --- | --- | --- |
| Обзор | Неразобранные обращения, требующие внимания клиники, подтверждённые сбои; переход в отфильтрованный список | «Нет обращений» только при успешной загрузке; неизвестные метрики не нули |
| Клиники | Поиск, состояние настройки/сервиса, контакт владельца в разрешённом объёме, последняя активность с определением; create только admin | Нет клиник → действие admin; нет результатов → сброс фильтров; ошибка → повтор |
| Карточка клиники | Идентификация, настройка, подключения, обращения, история разрешённых действий | Недостаточно прав, отсутствующая сущность, частичная недоступность секции |
| Поддержка | Очередь, назначение, статусы, поиск, фильтры «мои»/«без ответственного», дата последнего ответа | Нет обращений / нет совпадений отдельно; ошибка не очищает очередь |
| Карточка обращения | Тема, клиника, автор, ответственный, статус, публичная переписка; отдельно внутренние заметки | Черновик сохраняется при ошибке; конфликт версии предлагает обновление; закрытое обращение явно обозначено |
| Операции | Наблюдаемое состояние компонентов, сбои, свежесть, безопасная причина, ссылка на клинику | Нет наблюдения, устарело, источник недоступен; никакого зелёного статуса из отсутствующих данных |

В карточке клиники достаточно вкладок «Сводка», «Поддержка», «История»;
настройки и подключения раскрываются из сводки по разрешённым действиям.
Перед созданием обращения из карточки клиника уже выбрана; из общей очереди
её нужно выбрать. Создание сотрудником не подменяет автора на владельца клиники.

Список хранит search/filter/page в URL, возвращение из карточки восстанавливает
контекст. Серверная пагинация и стабильная сортировка обязательны.
Даты показываются с понятной timezone; статус не кодируется только цветом.
Действия доступны клавиатурой, focus возвращается после закрытия диалога,
ошибка формы связана с полем. Мобильный экран сохраняет главное действие и
переписку; таблица не должна требовать горизонтальной прокрутки для ответа.
Проверить RU/KK/EN, длинные значения, narrow viewport и отсутствие доступа.
Использовать существующие tokens, типографику, компоненты и API-layer.
Каждый видимый блок имеет данные, навигацию, действие или системный статус.

## 5. Ручное создание клиники

Предлагаемый мастер: сведения о клинике → будущий владелец → проверка → создание.
Минимум: название, поддерживаемый тип бизнеса, timezone, locale и email владельца.
Дополнительные реквизиты не делать обязательными без существующего требования.
Проверка перед отправкой показывает создаваемую клинику и адрес приглашения.

Backend проверяет admin и свежий MFA; создаёт Business и согласованный начальный
набор в транзакции, пишет audit и возвращает стабильный результат.
Повтор с тем же idempotency key не создаёт вторую клинику или приглашение.
Одинаковый ключ с другим payload отклоняется. Название само по себе не unique-id.
Проверять существующий email без сброса пароля, изменения чужой роли или
переноса существующей клиники. Совпадение владельца не означает дубль Business.
Если запрос откатился, не оставлять частичную membership, defaults или audit успеха.

Предпочтительный способ подключения владельца — приглашение с ограниченным сроком,
одноразовым принятием и проверкой адресата. Сотрудник не задаёт известный ему пароль.
Юридические подтверждения даёт сам владелец при принятии; платформа не подделывает
`accepted_documents`. Точный способ доставки и жизненный цикл приглашения требуют
решения до реализации этой части. Автоматическая внешняя рассылка здесь не разрешена.

Переиспользовать defaults и membership-логику из
[signup](../../apps/accounts/views.py) и [business activation](../../apps/businesses/activation.py)
после выделения подходящих общих операций. Landing activation требует landing_id,
имеет собственную ownership/subscription/pilot-pipeline семантику и не подходит
как готовый generic onboarding. Не сбрасывать подписку существующего Business.
Создание клиники не означает платную подписку или согласие на списание.

Существующая [CRM idempotency](../../apps/core/idempotency.py) привязана к Business.
Для операции до появления Business нужен scoped claim по actor/action/key;
не создавать фиктивную клинику ради idempotency. Решение должно доказать поведение
при конкурентных запросах и сбое между commit и ответом клиенту.

## 6. Обращения поддержки

Предлагаемые сущности:

| Сущность | Обязательные свойства и ограничения |
| --- | --- |
| SupportCase | Business, номер, тема, автор, source=clinic/platform, status, assigned_to, created/updated/resolved_at, version |
| PublicMessage | Case, реальный автор, текст, время; публичная переписка только в разрешённом Case |
| InternalNote | Case, сотрудник, текст, время; отдельный selector/serializer, никогда не отдаётся clinic API |
| CaseEvent | История назначения, смены статуса и восстановления; actor, old/new, время, безопасная причина |
| ReadState | Последнее прочитанное публичное сообщение для разрешённого участника; не считать unread из общего количества |

На первом этапе без вложений, удаления истории и внешних уведомлений.
Обращение обязательно связано с клиникой. Ответственный — активный сотрудник
платформы, не произвольный User и не обязательно BusinessMember клиники.
При потере роли прекращается доступ; незавершённые назначения видны для ручного
переназначения. Автопереназначение без политики не вводить.

Предлагаемый lifecycle:

`new → in_progress → waiting_clinic / waiting_internal → in_progress → resolved`.

Возврат из `resolved` в `in_progress` — отдельная операция с причиной и событием.
Нужность причины при решении, право автора закрывать/возобновлять и автоматическое
возобновление от ответа должны быть закреплены до соответствующей реализации.
Пока нет решения, не вводить скрытые переходы от любого сообщения.
Статусы ожидания сохраняют ответственного; назначение не означает решение.

Все изменения проходят сервис, проверку разрешённых переходов и optimistic lock.
Конкурентное изменение возвращает conflict, а не молча перезаписывает коллегу.
Создание и отправка сообщений идемпотентны; повтор после timeout не дублирует ответ.
Внутренняя заметка и публичный ответ — разные явные действия с разными endpoint.
Нельзя одним флажком случайно сделать сохранённую внутреннюю заметку публичной.

В CRM кнопка «Поддержка» открывает список доступных обращений и форму: тема, текст.
Business берётся из проверенного tenant-контекста, а не доверенного payload.
После отправки показывается номер и состояние. Ошибка сохраняет введённый текст.
При 403 нет данных других пользователей или клиник; при недоступности поддержки
обычная CRM продолжает работать. Обращение не является разрешением читать пациентов.

Рекомендуемая, но пока не утверждённая область видимости: сотрудник клиники видит
свои обращения, owner/admin — все обращения своего Business. Это отдельное
решение о приватности; до него нельзя реализовать «все видят всё» по умолчанию.
In-app уведомления могут использовать существующий механизм после проверки
получателей; закрытие доступа исключает будущую доставку и чтение.
Содержимое внутренних заметок не попадает в уведомления, логи и clinic search.

## 7. Операционное состояние

Разделить три независимых измерения:

- Настройка: какие обязательные для выбранного сценария шаги выполнены.
- Сервис: что реально наблюдалось у worker, webhook, queue, AI и других компонентов.
- Использование: последнее действие/событие, без вывода «сломано» из отсутствия продаж.

Каждый сигнал содержит источник, observed_at, состояние свежести и scope.
Допустимы healthy/degraded/down/unknown; stale отмечается отдельно.
`null` означает неизвестное значение; `0` — измеренный ноль.
`generated_at` ответа не заменяет время последнего наблюдения компонента.
Наличие broker URL не доказывает работающий worker или доставленную задачу.
Ошибка одного источника не должна обнулять весь overview.

Инцидент — наблюдаемый эпизод сбоя с безопасным идентификатором и временем.
Обращение — работа с человеком. Их можно явно связать; каждый сбой не должен
автоматически создавать обращение или уведомлять всех сотрудников.
Для каждого показателя определить numerator/denominator, interval, exclusions
и действие сотрудника. MRR/подписки сохранить отдельным финансовым блоком:
оценка по активным подпискам не равна фактической выручке. Не использовать
отсутствие платных подписок как сигнал сбоя. Удалять только доказанно лишнее,
а не то, что временно не используется в пилоте (уточнение владельца).
Не выводить токены, provider payload, тексты сообщений пациентов и raw traceback.
Не придумывать SLA, RPO или обязательные численные пороги без требований среды.

## 8. Backend и API

Сохранить существующие GET `/api/platform/overview/`, `operations-health/`,
`merchants/`, `merchants/{id}/` и журнал `merchants/{id}/support-actions/`.
Расширять совместимо или явно мигрировать всех callers; URL UI не обязан
повторять внутреннее имя merchants. Старая история не мигрирует в Case автоматически.

Предлагаемые новые контракты, ещё не существующие endpoints:

| API | Назначение |
| --- | --- |
| POST `/api/platform/merchants/` | Ручное создание с MFA/idempotency; возвращает clinic и состояние подключения владельца |
| GET/POST `/api/platform/support-cases/` | Очередь и создание сотрудником |
| GET `/api/platform/support-cases/{id}/` | Безопасная карточка и версия |
| POST `.../{id}/assign/`, `.../{id}/transition/` | Явные доменные команды с version |
| GET/POST `.../{id}/messages/` | Публичная переписка с пагинацией |
| GET/POST `.../{id}/internal-notes/` | Только platform API, отдельная выдача |
| GET/POST `/api/support/cases/` | Список/создание в проверенной clinic-области |
| GET `/api/support/cases/{id}/`, GET/POST `.../messages/` | Разрешённая публичная карточка и переписка |

Фильтры: business (только platform), status, assignee, search, page/page_size.
Задать допустимые значения, максимальный page_size и стабильный ordering.
Ответы содержат count/results и навигацию; счётчики вычисляются тем же scope.
Сервер валидирует длины, пустой/пробельный текст и недопустимые поля.
Ошибки различают validation, denied/not-found, conflict, throttling и unavailable;
не раскрывают существование чужого Case или email больше действующей политики.

Views: auth/validation → services → сериализация. Selectors отвечают за scoped
чтение; сервисы — lifecycle, transaction, idempotency и audit.
Уведомления только после commit, с повторяемой доставкой без дублей.
Значимые изменения пишут историю; sensitive/destructive операции — audit.
BusinessEvent создаётся только при реальном потребителе по текущему контракту,
а не как универсальная копия каждого сообщения. Новый AI-сценарий не добавляется.

## 9. Карта повторного использования и удаления

| Область | Решение |
| --- | --- |
| `apps/core/platform_views.py`, `platform_selectors.py`, `platform_serializers.py` | Сохранить проверенные read APIs, выделять сценарии без переписывания ради структуры |
| `apps/core/operations_health.py` | Уточнить data quality/freshness и обработку частичных сбоев |
| `apps/accounts/views.py`, `apps/businesses/activation.py` | Использовать проверенные defaults, не переносить целиком signup/landing-семантику |
| `apps/core/security_views.py`, account roles, grants/MFA/audit | Сохранить защитные границы и regression coverage |
| Новый support domain | Models/services/selectors/serializers/tests; точное размещение выбрать по существующей структуре apps |
| `frontend/src/api/platform.ts` и types | Расширить контракты; UI не делает raw fetch |
| `PlatformOverviewPage`, `PlatformMerchantsPage`, `PlatformMerchantDetailPage`, `PlatformOperationsPage` | Перестроить постепенно с сохранением доказанных flows |
| `PlatformLayout.tsx`, `frontend/src/app/router.tsx` | Компактная навигация, проверенные redirects/returnTo и guards |
| `PlatformPlaceholderPage.tsx` | Удалить только после удаления всех imports/routes и решения по старым URL |
| Shared UI/i18n | Переиспользовать; новые тексты через ключи, без общего редизайна CRM |
| `tests_platform_s02.py`, `tests_platform_operations.py` | Сохранить и расширить по изменённым контрактам |

Удаление допускается после inventory callers/imports/routes/tests, замены
пользовательского сценария и целевых проверок. Не удалять production-историю,
миграции или AuditLog под видом очистки интерфейса. Работать в каноническом checkout.

## 10. Проверяемая приёмка будущей реализации

| Область | Обязательные доказательства |
| --- | --- |
| Onboarding | Admin happy path; manager/clinic denied; MFA; existing email; payload validation; defaults; rollback; concurrent duplicate; retry после commit |
| Support | Оба источника создания; lifecycle; assignment только активному platform staff; version conflict; message idempotency; reopen по принятой политике |
| Privacy | Cross-Business/cross-Case IDOR; запрет internal notes в clinic API/search/notification; role loss; отсутствие расширения grant |
| Operations | healthy/degraded/unknown/stale; частичная недоступность; отсутствие schema/данных не превращается в нули; configured не равно observed |
| UI | Реальные API; create → list → detail; clinic request → staff response → clinic view; loading/error/empty/retry/403/conflict; draft preservation |
| Accessibility | Keyboard/focus, narrow viewport, длинный текст, RU/KK/EN; статус понятен без цвета |
| Migration | Чистая isolated DB, upgrade на применимых fixtures, drift/system checks; старая история сохраняется |
| Retirement | Нет ссылок на удалённые компоненты; старые URL обработаны осознанно; существующие read APIs/защитные сценарии не сломаны |

После каждого связного backend-перехода — focused tests до зависимого UI.
На закрытии — affected/dependent suites, system/schema/migration checks,
frontend build/types и целевые browser flows по [testing guide](testing.md).
Полный E2E не запускать автоматически из-за количества файлов; production/live
готовность требует отдельного target и согласованной эксплуатационной проверки.

## 11. Решения перед зависимой реализацией

| Вопрос | Рекомендация | Что именно зависит |
| --- | --- | --- |
| Доставка и принятие приглашения владельцем | Одноразовое приглашение, принятие документов владельцем; выбрать канал и срок | Завершение onboarding, не список клиник |
| Кто видит обращения внутри клиники | Автор — свои; owner/admin — все своего Business | Clinic selectors/UI и уведомления |
| Закрытие/возобновление | Сотрудник решает с итогом; явное возобновление; отдельно решить право автора | Только эти переходы |
| Редактирование, удаление, retention | Не вводить редактирование/удаление истории в первой реализации; срок хранения согласовать отдельно | Будущие lifecycle/retention jobs |
| SLA и эскалации | Пока без обещаний и автоматических эскалаций | Только метрики просрочки и automation |

Эти вопросы не отменяют уже утверждённые создание admin-only и оба канала поддержки.
Они блокируют только зависимое поведение; не требуют повторного согласования
каждого файла или обычного технического шага.
