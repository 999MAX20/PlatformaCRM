## Причины в коде

1. Многократные чтения одного членства и разрешений внутри GET. Профиль сотрудника
   выполнял281 SQL, большая страница задач623. Дополнительно `.only()` не загружал
   FK роли и провоцировал deferred lookup на каждом разрешении.
2. Подсчёты клиентов выбирали полный набор подробных вычисляемых полей и DISTINCT.
   Это запускало коррелированные подзапросы по всем10000 клиентам бизнеса даже
   для простого count. Четыре activity-facet счётчика запускались отдельно.
3. LIMIT страницы применялся после вычисления подробных полей и сортировки всех
  10000 клиентов. EXPLAIN показал external merge sort перед выдачей50 строк.

Исправление1: только свежий User, созданный JWT authentication для GET/HEAD,
содержит локальный на время запроса набор членств/прав. Следующий HTTP-запрос
заново читает БД. POST/PATCH/DELETE, JWT/device/auth_epoch и фоновые процессы
не используют этот набор. Решения по объекту/OWN/TEAM/филиалу не кешируются;
support grant по-прежнему проверяет актуальное expiry. SSE использует прямой
`get_user` при повторной авторизации и не получает snapshot.

Исправления2–3: count выбирает уникальные PK; summary выбирает только нужные
признаки; activity facets объединены в один aggregate. Пагинация сначала выбирает
разрешённые и отфильтрованные ID с исходной сортировкой, затем обогащает только
строки страницы и возвращает их в порядке этих ID. Повторный запрос также сохраняет
исходный tenant/scope/filter queryset. API-поля, значения, quick filters, summary
вне quick-filter/pagination и сортировка сохраняются.

## Что относится к компьютеру

Windows, Intel Core i3-1315U,6ядер/8потоков,7.7GiB RAM. API, PostgreSQL,
генератор нагрузки и пользовательские приложения работают на одной машине.
Исходные нагрузочные прогоны имели только108–711МБ свободной RAM и значительную
общую загрузку CPU. Мы не останавливали чужие приложения/службы.

При диагностике median нового PG connection≈29мс, SELECT1≈0.52мс,
health без БД≈0.35мс. Это не объясняет2–4с в списке клиентов. Windows snapshot
при500МБ свободной RAM показал PageReads/sec=0 и PagesInput/sec=0: низкая свободная
память сама по себе не доказывает дисковый paging. Ресурсные показатели каждого
нагрузочного этапа сохранены. Точные доли задержки от чужих приложений/планировщика
не установлены: изолированного второго компьютера для контрольного сравнения нет.
Изменение SQL-работы доказано планами, а не выведено из одной вариации latency.

Позднее, во время HTTP-нагрузки, зафиксирован уже реальный paging:
`CommittedBytes=23062507520` при7.7GiB физической RAM,
`PageReadsPersec=8570`, `PagesInputPersec=24284`; минимум свободной памяти
на одном этапе3.6МБ. Это snapshot, не среднее всей серии.
Тестовый API имел110145536→111742976 private bytes в двух последовательных снимках
(примерно105→107MiB), worker≈97MiB, controller≈34MiB. Процесс API не объясняет
23GB system commit; значительная фоновая память/работа принадлежала другим
приложениям, WSL и системным службам. Два снимка не сертифицируют отсутствие
долговременных утечек. Файлы `memory-pressure-*.json` сохраняют измерения.
