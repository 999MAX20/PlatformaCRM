# AI-WORK-CRM-COMPLEX-20261112

Поручение: проверить «Работу с CRM» на нескольких действиях, уточнениях,
исправлении запроса, архивных записях и ограничениях прав через Playwright/API
с реальным AI; прочитать [AI-REQUEST-APPOINTMENTS](ai-request-appointments-20261111.md).
Проверка завершена с открытыми C1–C3 ниже. Исправления продукта не входили в поручение.

## Выводы

### C1 — P1: второе независимое создание получает значения первого

API-запрос: две отдельные задачи «QA Сверить кассу»/«QA Проверить доставку»,
описания «Смена один»/«Смена два». Router создал два разных шага, но оба предложения
crm_create содержали первую задачу и её описание. В Chrome повторено с другими
названиями: «QA Браузер Касса»/«QA Браузер Доставка» — обе карточки предлагали кассу.
Неверные предложения не подтверждались: второй запрос пользователя остаётся
невыполненным, подтверждение такого набора рискует создать дубли первой задачи.
Фактическое создание этих ошибочных дублей в данном прогоне не проверялось.

Доказательства: `turn-multi-independent.json`, `complex-results.json`,
`browser-multi-turn.json`, `browser-multi.png`, `browser-results.json`.
В сохранённых request logs2/3 разные command_context.selected_step, но одинаковые
output values. `crm_planner.py:158–173` передаёт общий original_request как user_input,
а selected_step остаётся контекстом; `conversation_preparation.py:100–110` принимает
результаты без проверки различия запрошенных независимых созданий. Это локализация
границы ошибки, не доказательство единственной причины поведения модели.
Зависимые Client→Task и Appointment→Task, а также изменение двух разных задач прошли.

Условие закрытия: обе независимые задачи имеют собственные значения до подтверждения;
после подтверждения созданы ровно две требуемые записи, replay не добавляет дублей;
сохранить зависимые цепочки и требования подтверждения.

### C2 — P2: чтение архива подменено недоказанным отказом доступа

Владелец просил показать архивную задачу с ID и названием. API и Chrome возвращают
completed/no_data и утверждение «Доступ к архивным задачам отключен», без описания
существующей записи. Тот же владелец затем успешно восстанавливает запись.
`conversation_preparation.py:122` вызывает read_entities без include_archived;
`crm_tools.py:98–101` по умолчанию исключает архив. Read-route не передаёт требование
включить архив. Отсутствие строки в таком наборе не доказывает запрет прав.

Доказательства: `turn-archive-read.json`, `browser-archive-read-turn.json`,
`browser-archive-read.png`, baseline/final SQL. Изменение архива до восстановления
запрещено, выбор между активным и архивным дублем уточняется, restore→update прошёл.
Это отдельный пробел чтения/grounding; не разрешение менять архивные записи напрямую.
Условие закрытия: доступный архив читается по явному запросу в разрешённом scope либо
честно сообщается ограничение функции; права не выдумываются, скрытые строки не раскрываются.

### C3 — P2: карточка заявки недостаточно понятна для подтверждения

В RU-карточке Appointment после уточнения на390px поле филиала показывает
`aiCRM.field.branch`; клиент/услуга/специалист/филиал — ID3/4/5/1 вместо названий.
Дата показана сырым ISO. В `AgentTurnCard.tsx:44–47` values выводятся через String,
ключ поля конструируется; перевод aiCRM.field.branch отсутствует. Это обнаруженный
недочёт проверки предложения человеком, не обход серверных прав.
Доказательства: `browser-app-corrected.png`, `browser-app-corrected-aria.txt`.
Горизонтальная прокрутка таблицы предусмотрена; её наличие не записано как дефект.
Условие закрытия: локализованное поле филиала и понятные разрешённые названия связей/
дата доступны перед подтверждением, без раскрытия недоступных данных.

## Проверка указанного отчёта

Принято актуальное правило: новая заявка/лид/өтінім создаётся как Appointment;
обязательные клиент/услуга/специалист/будущее время уточняются. Старое W3 с Lead-create
из этого чата заменено предыдущим отдельным поручением; текущий прогон его не повторяет.
Исторический Lead обновлён без создания Lead/Deal. Новые Appointment подтверждены
в сложной цепочке и после уточнения времени.

Наблюдение отчёта о занятости подтверждено: конфликт допустим в предложении,
проверка при исполнении отклоняет Appointment; ранее подтверждённая задача остаётся,
retry не создаёт новых Task/Appointment. Предварительная подсказка о конфликте не доказана.

Точный прежний сбой `AIResourceBookingTests.test_plan_checks_shared_equipment_between_different_specialists_before_writes`
на текущем коде **1PASS**, `equipment-exact-recheck.log`. Сначала дополнительно
запущен соседний busy-equipment тест — также1PASS, `equipment-recheck.log`.
Оба в isolated_runtime, системная проверка чистая. Изменения оборудования принадлежат
другому поручению; этот чат их не исправлял. Прежний зависимый64-case FAIL остаётся
