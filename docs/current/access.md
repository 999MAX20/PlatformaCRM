## К11: доступ к корректирующей версии

POST `/api/medical/documents/versions/{id}/correction/` принимает точную текущую
версию/state_revision, исправленный текст, причину и Idempotency-Key. Основной врач
должен иметь текущий UPDATE, филиал, проверенную идентичность и основание записи,
участия либо ранее утверждённое разрешение на этот документ ровно на24ч.
Разрешение не создаётся автоматически и не заменяет SIGN/APPROVE. Медруководитель
не становится основным автором: его подтверждение остаётся отдельным действием.
Review/sign/PDF/finalize принимают correction_access_id только для подтверждённой
корректирующей версии; обычные ограничения сохранены. Истечение/отзыв проверяются
снова, включая повтор запроса. Права не расширяются до другого пациента/документа.
Ответы private/no-store; новый черновик и отказы аудируются, сбой откатывает переход.

## К11: собственное завершение участия

GET `/api/medical/participations/{id}/closure/` возвращает состояние и постраничный
перечень обязательств (offset/limit≤50); требуется VIEW и UPDATE своего участия,
текущий филиал и роль. Медруководитель получает эту проекцию через as_head=true
с MANAGE. Клиническое содержание не возвращается. Терминальное участие даёт409.
POST `.../{id}/end-own/` принимает business_id/patient_id/expected_revision и
Idempotency-Key; повтор заново проверяет текущие права. Незакрытые записи, приёмы
и обязательные документы блокируют собственное завершение. Ответы private/no-store;
чтения, переход и отказы аудируются. Независимые основания доступа сохраняются;
разрешение исправлений на24ч автоматически не возникает.

## К10: оформление фактического визита

GET `/api/medical/encounters/actual-context/` и POST `.../actual-visit/` проверяют
текущие медицинские права CREATE medical_patients, филиал, CRM CREATE appointments
и VIEW clients. Врач оформляет только себя; медруководитель и ресепшн выбирают
действующего врача своего доступного филиала. У назначенного врача обязательна
текущая роль doctor/head и CREATE medical_records. Текущий день определяется
часовым поясом бизнеса; более ранний день разрешён только медруководителю с причиной.
Причина и связь с исходными временем/пациентом/автором зашифрованы. Сохраняются
проверки каталога, расписания, пересечений, идемпотентности и аудита. Ответы private/no-store.
Миграция0051 additive; обратное удаление существующей истории запрещено. Рабочая БД не менялась.

## К10: доступ к завершению приёма

GET `/api/medical/encounters/{id}/completion/` и POST `.../{id}/complete/` требуют
основного врача, текущей роли UPDATE medical_records, филиала и основания записи
либо участия. POST принимает expected_revision, expected_appointment_updated_at,
reason и Idempotency-Key; календарный переход дополнительно проверяет CRM UPDATE.
Ответы private/no-store; чтение и завершение аудируются, HTTP-отказы фиксируются
без чужих идентификаторов пациента. После завершения основание записи прекращается:
повтор без другого действующего основания получает отказ, а не открывает историю.
Миграция0050 добавляет действие аудита; обратная миграция с такой историей запрещена.
Рабочая БД не мигрирована; реальная ЭЦП/формы не сертифицированы этим сценарием.

## К08: локальный API и просмотр PDF-черновика

Локально проверенный сценарий передачи документа на проверку:
GET `.../versions/{version_id}/review/` читает состояние и историю точной версии
по четырём текущим основаниям, с курсором `before_id`/`limit` и аудитом чтения.
POST `.../versions/{version_id}/review-transition/` принимает appointment либо
participation, `expected_state_revision`, `target` и `reason`, заголовок
`Idempotency-Key`. Основной врач с текущим UPDATE переводит draft в ready_for_review
и обратно; возврат требует причины. Временное исправление и область руководителя
сами по себе не разрешают этот переход. По решению владельца23.11.2026 основной
врач может подтвердить содержание любой внутренней версии: ready_for_review →
reviewed («Проверено врачом»). Это внутреннее подтверждение точной версии,
без финализации, ЭЦП и права выдачи пациенту. Возврат reviewed → draft требует
причины, снимает текущее подтверждение, сохраняет событие в истории. Состояние имеет отдельный
счётчик, текст/PDF остаются неизменными; редактирование запрещено вне draft.
История, зашифрованная причина и аудит сохраняются атомарно. Миграция0039
блокирует разрушительный reverse при истории проверки;0040 сохраняет историю
подтверждения даже после возврата в draft. Рабочая БД не мигрирована. Backend,
desktop/mobile подтверждения и итоговая frontend сборка проверены локально
(точный срез и ограничения публикации — в checkpoint).

POST `/api/medical/documents/versions/{version_id}/pdf-prepare/` подготавливает
неизменяемый приватный PDF выбранной версии; повтор возвращает прежний artifact.
GET `/api/medical/documents/versions/{version_id}/pdf/` возвращает внутреннее inline
представление после проверки сканером, контрольной суммы, текущих прав и аудита.
Оба входа требуют `business_id`, `patient_id`, `language` (ru/kk/en) и ровно одно
основание: `appointment_id`, `participation_id`, `correction_access_id` или
`head_branch_id`. Требуется medical_documents VIEW и medical_records VIEW;
временное разрешение ограничено конкретным документом, медруководитель своим
филиалом. Общие file permissions, owner и platform admin не дают обхода.
POST `/api/medical/documents/versions/{version_id}/pdf-download/` и `pdf-print/`
повторно проверяют medical_documents EXPORT и текущее основание, сканер и
целостность, затем пишут document_exported/document_print_requested с версией.
Первый возвращает attachment, второй inline. Событие печати фиксирует запрос,
а не физический результат. pdf-prepare возвращает scoped can_export для кнопок;
последующий экспорт заново проверяет права. Кнопки и API проверены локально.
В текущей реализации К08 POST `docx-prepare/` и `docx-download/` на той же версии
требуют EXPORT уже при подготовке, текущее основание и сохранённое разрешение DOCX
по виду документа. Разрешена только текущая draft revision с источником утверждённого
шаблона; legacy/ненастроенные документы, исторические версии и состояния проверки
не получают это право. Приём должен оставаться draft либо предоставлено действующее
узкое correction основание; архивированная медкарта не допускается. Скачивание
повторно проверяет условия, сканер, контрольную сумму и обязательный аудит.
PDF prepare возвращает дополнительный `can_docx` для интерфейса; это не разрешение
обойти проверку следующего запроса. DOCX содержит маркировку черновика; изменение
скачанного файла не изменяет CRM. Сервер/API/гонки и desktop/mobile экспорт,
ошибка/повтор/конфликт проверены локально; полный сценарий К08 остаётся в работе,
см. DENTAL-MCS checkpoint.
Для шаблонов добавлен локально проверенный POST
`/api/medical/document-templates/versions/{version_id}/docx-download/`
с `business_id` и языком RU/KK/EN. Требуются VIEW и EXPORT: личный шаблон доступен
его владельцу, общий черновик медруководителю с business scope, утверждённый общий
шаблон врачу. Шаблон должен быть активен и явно разрешён текущими правилами вида.
Выгрузка сохраняет поля-подстановки и маркировку черновика. После генерации и
проверки сканером сервер повторяет авторизацию и проверку версии правил; при
изменении правил требует повторить операцию. AuditLog DOWNLOAD содержит ID
шаблона/версии/правил, язык и хеш без текста. Файл формируется в памяти; CRM не
импортирует его изменения. При сбое сканера/аудита байты не выдаются.
GET `versions/{version_id}/docx-access/` на том же ресурсе принимает `business_id`:
без EXPORT/opt-in возвращает `can_docx=false`, без VIEW возвращает403. Подсказка
не заменяет проверку POST. Действие подключено к карточке шаблона и форме врача;
полный К08 остаётся в работе.
Серверный контур (опубликован64dec3e6): POST
`/api/medical/documents/versions/{version_id}/head-confirm/` принимает business_id,
patient_id, head_branch_id, expected_state_revision и Idempotency-Key. Требует
действующего медруководителя с APPROVE в филиале, VIEW точной версии и проверенную
идентичность пациента. Сохранённые правила должны содержать medical_head.
Подтверждение связано с текущим направлением на проверку; оно не меняет состояние
проверки основным врачом и не является подписью. Возврат в черновик сохраняет
историю, но снимает актуальность подтверждения. Повтор команды проверяет текущие
права до возврата прежнего результата. Запись и отдельное событие аудита атомарны.
GET `versions/{version_id}/head-review/` поддерживает четыре прежних основания
чтения; возвращает требование, доступность действия и текущую отметку. Ответы
private/no-store, отказы аудируются. Backend/API и основной RU desktop/mobile интерфейс проверены локально;
браузерные409/403, RU/KK/EN и конкуренция PostgreSQL также проверены в этой
границе. Откат0045/0046 запрещён при наличии истории подтверждений/аудита;
пустой roundtrip и сохранение прежнего снимка проверены изолированно. Миграции0045/0046 только в изолированной тестовой
БД, к рабочей БД не применялись.

Контур подписания точной версии: GET `versions/{version_id}/signing/`, POST
`prepare-signing/`, `start-signing/`, `advance-signing/` и GET `signing-pdf/`.
Подготовка/подписание требуют текущих VIEW/SIGN и основания в филиале, проверенной
идентичности, активной карты, сохранённых обязательных полей и проверок содержания.
Запускает основной врач; дальнейший порядок primary_clinician/medical_head/
patient_or_representative берётся из снимка матрицы. Сейчас доступен только явно
тестовый адаптер: действие пациента имитирует основной врач, это не подтверждение
личности или настоящая подпись пациента. Флаг MEDICAL_SYNTHETIC_SIGNING_ENABLED
по умолчанию выключен; production/staging запрещены независимо от флага.
Очередь привязана к конкретному циклу проверки и неизменяемому signing-PDF.
Старый draft PDF и его манифест сохраняются. Просмотр подписываемых байтов требует
SIGN, чистого файла, совпадения хеша/манифеста и аудита; это не выдача пациенту.
Повтор проверяет текущий доступ, ожидаемая ревизия защищает отмену и поздние действия;
зашифрованное свидетельство связывает файл, сессию, шаг, автора и порядок. Возврат
на исправление делает прежний цикл непригодным для продолжения. Миграции0047/0048
защищают историю от обратного удаления. Рабочая БД и реальный провайдер не изменены.
Состояние completed с adapter=synthetic не является юридически значимой ЭЦП
или разрешением реальной выдачи. Реальные callback/сертификаты/desktop/mobile — L06.

POST `versions/{version_id}/finalize/` завершает проверенный тестовый документ:
основной врач с текущими UPDATE/SIGN указывает точный signing-artifact и ревизию
состояния. Обязательные подписи должны быть завершены для этого же PDF/цикла;
при отсутствии требования подписи сессия не выдумывается. Сохраняется отдельная
MedicalDocumentFinalization с защищёнными ссылками и зашифрованным свидетельством.
Состояние finalized запрещает обычные edit/return; повтор команды вновь проверяет
права и не создаёт второй финализации. История и проверка медруководителя сохраняются.
Просмотр финального PDF требует текущего VIEW/основания и проверку сохранённого
свидетельства/байтов; SIGN нужен для работы с ещё не финализированным signing-PDF.
Финализация и аудит атомарны; конкурентные finalize/return имеют одного победителя.
Миграция0049 блокирует обратное удаление финализированных документов. Проверена
только изолированно. Финализация пока явно тестовая, под тем же выключенным по
умолчанию флагом; реальная выдача и связанные окончательные исправления ещё открыты.

GET `/api/medical/documents/versions/{version_id}/requirements/` в текущем рабочем
срезе проверяет VIEW и одно действующее основание (запись, участие, исправление,
филиал медруководителя), как доступ к артефакту. Возвращает наличие обязательных
полей из сохранённого снимка без самих значений, признак текущей версии и ID правил.
Текущие данные клиента/клиники не заполняют старую версию задним числом. Без
сохранённой матрицы `configured=false`, `fields_complete=false`. Полнота полей не
является подписью, финализацией или разрешением выдачи. Ответ private/no-store,
чтение и отказы аудируются. Серверная проверка и RU desktop/mobile сценарий с повтором после503 и очисткой
при403 пройдены локально; срез опубликован64dec3e6.

GET `/api/medical/documents/versions/{version_id}/export-history/` принимает
`business_id`, `patient_id`, одно из тех же четырёх оснований и необязательные
`before_id`/`limit` (1–50, по умолчанию20), без параметра языка. Требует текущий
VIEW точной версии, а не EXPORT; возвращает только успешные скачивания и запросы
печати этой версии, сотрудника, время и revision. Чтение, включая пустую историю,
аудируется до ответа; сбой аудита блокирует выдачу. Ответ private/no-store.
Миграции артефактов и событий экспорта запрещают разрушительный откат при
наличии этих данных. Пустая новая структура допускает обратный переход;
при отказе отката следует сохранить данные и вернуться к текущей схеме,
а не удалять документы/аудит. Сохранность и PG-гонки проверены изолированно;
это не применение миграций к рабочей БД и не проверка эксплуатационного backup.
Это не выдача пациенту или ЭЦП. Ответы private/no-store;
PDF дополнительно nosniff/sandbox, storage URL не раскрывается. Подготовленный файл
остаётся в карантине до проверки. Отказ в доступе фиксируется без чужих patient IDs.
Configured logo берётся из сохранённого URL по pinned public HTTPS, нормализованные
bytes фиксируются вместе с первым артефактом версии и переиспользуются для её
следующего языка без повторного обращения к URL. Повреждённый manifest блокирует
создание нового файла; ошибка не приводит к молчаливому пропуску логотипа.
В существующей карточке документа подключён inline просмотр сохранённой версии;
смена пациента, основания, версии или языка уничтожает прежний viewer и отменяет
запрос. В форме временного исправления просмотр доступен для сохранённого draft
до появления несохранённых изменений. Сервер повторно проверяет точный документ
и действительность разрешения. Медруководитель читает список, историю и версии
через head_branch_id выбранного филиала; нужны также обычное право чтения клиента
и medical_records VIEW. Вход находится в медицинской вкладке карточки клиента;
отзыв доступа очищает представление. Desktop/mobile проверены локально; полная
приёмка К08 остаётся открытой. Границы доказательств — DENTAL-MCS checkpoint.

## Медицинская граница DENTAL-MCS — 22.11.2026

К07: `/api/medical/files/` требует `medical_records.view` и отдельное разрешение
`medical_files.view/create/export`. Сервер принимает ровно одно актуальное основание:
собственную запись, действующее участие, временное разрешение на конкретный приём
или назначенную область медруководителя. Разрешение на исправление отдельного документа
не даёт доступа к файлам приёма. Общие attachment API и admin не раскрывают medical
attachments даже владельцу или platform admin. Просмотр требует view, скачивание —
export; имя/описание/FDI читаются только после аудита. Непроверенные, заражённые и
изменённые после сканирования bytes не выдаются. Изменение описания/привязок требует
права create, авторства, допустимого состояния приёма, причины и актуальной revision;
прежняя версия сохраняется. Подписанные документы и их выдача — отдельные К08–К12.

К07 локальная реализация: общий `write_patient_audit` сохраняет первичный журнал внутри
savepoint. Только action=`read` после отказа первичной записи может использовать
явно настроенный защищённый резерв (`MEDICAL_READ_AUDIT_RESERVE`, operations.md).
Проверки роли/основания, Business, пациента и точных версий выполняются до этого.
Без подтверждённого резервного события ответ503 закрывает чтение; отсутствие
конфигурации сохраняет прежнее поведение. Изменения и `file_downloaded` резерв
не используют. Упоминания ниже «сбой аудита блокирует чтение» означают невозможность
надёжно записать ни основной, ни разрешённый резервный журнал; сбой аудита записи
по-прежнему откатывает изменение. Это локальный контракт, не облачная сертификация.

К05: `/api/medical/correction-access/` — отдельные requests, не TreatmentParticipation.
GET list (business/branch/client, head=false по умолчанию, cursor/limit1–50) возвращает
свои запросы; head=true требует текущий head +medical_records.manage/view в филиале.
GET targets выдаёт metadata собственных primary Encounter и документов без clinical
body; POST root принимает encounter/document, expected patient/target revisions,
reason≤2000 и Idempotency-Key. Pending не предоставляет чтение. POST id/review/
принимает approve/reject, expected_revision и причину; самосогласование запрещено,
approve повторно проверяет текущие права инициатора и версии источника.

Active действует ровно [reviewed_at, reviewed_at+24h); POST id/close/ допускает
withdraw собственного pending, complete собственного active либо revoke текущим
head. Terminal не переоткрывается; новое согласование — новый запрос с причиной.
GET id/target/ и POST id/save-draft/ повторно проверяют account/member/medical role,
Business/branch/CRM client и ровно указанную цель. Доступ по исправлению не открывает

## Экран после отключения доступа, 18.11.2026

`GET /api/auth/me/` возвращает `business_access_revoked=true`, когда у пользователя
нет доступных бизнесов и есть отключённое членство либо ранее принятое приглашение
на его текущий email (в том числе после удаления участия). Ответ не раскрывает данные
недоступного бизнеса. Новый пользователь без членств не получает этот признак;
владелец и сотрудник с другим доступным бизнесом продолжают обычную работу.
Merchant-маршруты в этом состоянии показывают отдельный блок «У вас больше нет
доступа к этому бизнесу» и выход из аккаунта, без рабочего меню и предложения
создать бизнес. Backend-проверки доступа сохраняются.

В настройках команды действие отключения находится в начале карточки сотрудника
и сохраняет подтверждение, аудит и историю. Принятые и отозванные приглашения
показывают итоговый статус без срока ссылки, ошибки старой отправки или предложения
отправить её повторно. Исторические данные доставки сохраняются на сервере.
Проверки и граница выкладки: [evidence](../testing/evidence/invitations-24h-20261112.md).

диагностику, но не писать support-note с grant/MFA. UI использует
`can_log_support_action`, POST повторно проверяет сервер. BE-GAP-004/D-09 решены.

Для staging/production/первого платного пилота `AUTH_PRIVILEGED_MFA_REQUIRED=True`.
Обязательные identities: superuser, platform_admin, platform_manager. Пользователи
бизнеса, включая owner и активные owner/admin memberships, подключают MFA добровольно
в кабинете. Регистрация, принятие приглашения и вход без подтверждённой MFA не
требуют enrollment. Настройка доступна каждому активному авторизованному пользователю;
фактор включается только после успешного подтверждения. Уже включённый фактор
обязателен при входе независимо от роли и значения этой настройки.

При включённой или обязательной MFA primary factor выдаёт одноразовый challenge,
не JWT-сессию до проверки фактора; иначе сразу выдаёт сессию CRM.
TOTP replay отсекается счётчиком, recovery codes одноразовые и хранятся хешами;
TOTP secrets зашифрованы keyring. Секреты/коды/refresh/challenge не логируются.
Вход Django admin применяет ту же политику MFA: TOTP или одноразовый recovery code
проверяется до создания административной сессии. Требуемый enrollment выполняется
через существующий вход CRM. Каждый admin route проверяет proof пользователя,
auth epoch и устройства; прежняя password-only сессия не обходит включённую MFA.
Вход admin ограничен по IP и идентификатору (`AUTH_ADMIN_LOGIN_RATE`, 5/min),
смена пароля — по пользователю (`AUTH_PASSWORD_CHANGE_RATE`, 5/min) до проверки
пароля/фактора. Общий Django Redis cache хранит квоты всех web workers;
`DJANGO_CACHE_URL` по умолчанию использует `REDIS_URL`. Недоступный cache не
разрешает попытку. DRF read/write throttling остаётся базовым abuse-контролем,
не атомарным пределом для одновременных запросов. Изолированные проверки явно
используют отдельный locmem cache; staging/production такой backend отвергают.
Password/security/MFA reset проверяют текущий пароль/фактор по своему контракту,
отзывают сессии и audit. Reset обязательной MFA требует повторного enrollment,
не выдаёт MFA-free platform session. После подтверждённого отключения добровольной
MFA пользователь бизнеса получает обычную сессию. Step-up привязан к user/auth epoch.
Нет фактора — только отдельно авторизованное восстановление после проверки
владельца; экспорт/восстановление старого секрета недопустимы.

## Сессии и личный аккаунт

ADMIN-03, решение16.10: при утрате всех доступов — обращение в поддержку и ручная
идентификация по ранее проверенным данным. Обе platform-роли со свежим MFA могут

[контракт ADMIN-03](../testing/platform-rebuild-spec-20261014.md#admin-03--согласованный-контракт-16102026).
Обычная передача Business в ADMIN-02 остаётся отдельной операцией.

- Access/refresh проверяют auth epoch; security-изменения отзывают прежние
  credentials. Нормальный tracked logout отзывает текущее устройство, не все
  другие. Старый sid-less logout сохраняет совместимое широкое отзывное поведение.
- Merchant session: idle 7 дней foreground-использования или absolute 30 дней
  от login, что раньше. Access default 15 минут. Background reads не продлевают
  idle; параметры в `config/settings.py`, не в клиентском таймере.
- Session API работает только для request.user, не по чужому user ID.
  Отзыв другого своего устройства idempotent, текущего через этот endpoint
  отвергается; enabled MFA проверяется. Список не выдаёт токены/JTI.
- Все операции refresh-cookie сериализуются; generation checks отвергают
  старые ответы/продолжения после смены аккаунта. Web Locks координируют вкладки
  на поддержанных origins; fallback остаётся per-page. BroadcastChannel не
  сохраняет credentials и не переключает открытую страницу на чужой аккаунт.
- Network/429/5xx сохраняют текущий аккаунт/URL/draft, дают bounded retry и
  Retry-After. Invalid/expired credentials требуют login. Бизнес-мутации не
  переигрываются автоматически после восстановления auth.
- Email/login change относится только к request.user, не меняет ID/memberships;
  требует пароль и enabled MFA, подтверждение одноразовым mailbox code.
  Обычный profile PATCH email не меняет. Подтверждение повторно проверяет
  доступность/epoch, отзывает старые sessions и выдаёт замену. Locmem-тест не
  доказывает SMTP-доставку.
- Принятие приглашения существующим email возможно только из сессии этого
  аккаунта; меняется membership, не пароль/глобальные атрибуты пользователя.
