## Реестр UI → API → хранение → использование

Общие границы: выбранный Business передаётся явно; сервер сначала ограничивает
доступный queryset, затем выбранный бизнес. Cache keys и формы привязаны к Business.
Списки настроек, сотрудников, ролей, приглашений и отделов загружаются со всеми
страницами. Ошибка не выдаётся за пустой список. UI вызывает только `src/api/*`.

### 1. Бизнес, четыре существующие группы

Форма [BusinessSettingsForm](../../frontend/src/components/forms/BusinessSettingsForm.tsx)
→ `PATCH /api/businesses/{id}/` → `Business`; запись требует `settings:update`.

| Параметр | Реальный потребитель и решение |
| --- | --- |
| Название | Имя бизнеса в интерфейсе, сообщениях и контексте; сохранено редактирование |
| Slug | Идентификатор Business; подпись больше не обещает адрес кабинета |
| Тип бизнеса | Метаданные контекста/onboarding/playbook, не переключатель вертикального интерфейса |
| Город, адрес, телефон | Сохранённые контакты; адрес используется в шаблонах записи |
| WhatsApp, Telegram, Instagram | Контактные реквизиты; сохранение не подключает канал доставки |
| Language | Сохранённая метаинформация, только чтение; язык интерфейса выбирается в личном профиле |
| Общий SLA | Только чтение: не смешивается с работающим SLA стадии/маршрутизации |
| Timezone | Расписание, локальные даты и сообщения; сервер проверяет идентификатор ZoneInfo |
| Booking buffer | Значение сохранено, редактирование убрано: этот параметр не управляет overlap/интервалами |
| Cancellation policy | Сохранённый текст только для чтения; не выдаётся за исполняемую политику отмены |
| Currency | Валюта денежных отображений/аналитики; редактирование сохранено |
| Legal name, tax ID, invoice email | Реквизиты Business; не подменяют отдельные реквизиты Subscription |
| Financial source mode | Существующий выбор manual или одного внешнего источника; Select отражает сохранённое значение |
| Financial connector | Только финансовые подключения того же Business; прежняя серверная проверка сохранена |
| Prepayment policy | Справочный текст только для чтения; не вводит обязательную предоплату |
| Brand color/logo | Сохранённые значения только для чтения; не обещают менять оформление кабинета |

Неактивные параметры исключены из payload формы; значения модели не удалялись.
Все четыре группы сохранены. Неверная timezone отклоняет запрос без частичной записи.

### 2. Команда

[Team API](../../frontend/src/api/team.ts) → `team/members`, `team/invitations`,
`team/departments` → BusinessMember/BusinessInvitation/Team; view/manage — текущие
права `team`, проверяемые по фактическому Business объекта.

| Параметр/действие | Хранение и реальный эффект |
| --- | --- |
| Выбор сотрудника | Навигация по полному списку участников текущего бизнеса |
| Роль сотрудника | Membership role + связанная BusinessRole; сохранены существующие пресеты |
| Область видимости | Вычисляется для выбранного сотрудника, не для последней открытой роли |
| Включение/отключение входа | Меняется членство/доступ; специалист, записи и история остаются; автоматического переназначения нет |
| Email, имя, роль приглашения | Сохранённое приглашение; default Operator совпадает с текстом интерфейса |
| Канал и контакт приглашения | Генерируют ссылку/подготовленное сообщение; открытие мессенджера не доказывает доставку |
| Копирование | Успех показывается только после успешной записи clipboard; ошибка имеет явное состояние |
| Отзыв приглашения | Существующее действие revoke, с серверной проверкой доступа |
| Название отдела | Создаёт Team; число участников берётся из реальной связи |

Подмена business/body при редактировании чужого membership/role не авторизует запись.
Перенос существующего объекта между Business запрещён. Audit и изменения атомарны.

### 3. Роли

Выбор роли — навигация. Кнопки NONE/OWN/TEAM/BUSINESS используют один
`POST team/roles/{id}/visibility/` → [role service](../../apps/businesses/role_services.py)
→ RolePermission.scope. Полный batch валидируется и сохраняется атомарно с audit.
`is_allowed` каждого действия сохраняется, то есть смена области не выдаёт новые
права. NONE затем OWN восстанавливает прежние разрешённые действия в новой области.
Отдельное редактирование конкретного permission сохраняет прежний API и назначение.
Несовпадающие области показываются как смешанные; summary учитывает просмотр/manage.
Некорректная группа «Экспорт», менявшая billing, убрана. Отдельного export-permission
нет в действующем каталоге; существующие проверки экспорта не менялись.

### 4. Безопасность

`security/risk-summary`, `audit`, `login-history`, `support-grants` → AuditLog,
LoginHistory, SupportAccessGrant. Это просмотр по `audit_logs:view`, не управление
правами поддержки. Owner + recent MFA для выдачи/изменения support grant сохранены.

| Показатель/список | Семантика |
| --- | --- |
| High + critical | Количество записей audit за всё время, не оценка риска компании |
| Failed logins | Число неуспешных входов за всё время в выбранном Business |
| Support | Только активные и ещё не истёкшие grants |
| События | Реальное действие, тип и ID объекта, actor, время, уровень; показаны все строки полученной ограниченной выборки |
| Входы | Реальные email, IP, время, статус; не подменяются нулями при ошибке |
| Grants | Реальные получатель, срок и статус, включая истёкшие разрешения |

Неверные фильтры дают 400; несколько доступных бизнесов без selector не выбираются
молча. Подписи периода/счётчиков не утверждают мониторинг или новый risk engine.

### 5. Сообщения по записи

`appointment-message-settings` → AppointmentMessageSetting →
[message settings service](../../apps/scheduling/message_settings.py),
[queue service](../../apps/scheduling/services.py),
[delivery](../../apps/notifications/delivery.py). Настройки требуют `settings:update`.

| Параметр | Реальный эффект |
| --- | --- |
| Confirmation / reminder / thank-you | Три существующих сценария; стабильная identity не редактируется |
| Enabled | Включает/отменяет соответствующие будущие незавершённые задания |
| Offset | Минуты до записи либо после её окончания; действуют серверные ограничения |
| Template | Разрешённые placeholders из реальных данных записи/клиента/бизнеса; неизвестные/небезопасные форматы отклоняются |
| Auto | Контакт + готовый активный Telegram, затем WhatsApp, затем email; иначе внутреннее уведомление сотруднику |
| Telegram/WhatsApp | Только локально готовое активное подключение, credential и соответствующий контакт; mock не считается готовностью |
| Email | Настроенный реальный mail backend; console/locmem/file/dummy не считаются клиентской доставкой |
| System | Внутреннее уведомление сотруднику; UI явно отличает его от сообщения клиенту |
| SMS | Новое назначение недоступно; существующее значение можно отключить/сменить, данные не стираются |

Правка настройки пересоздаёт только её незавершённый сценарий для подходящих записей.
Retry/SENDING claims отменяются; поздний worker не восстанавливает отменённый статус.
Изменение времени/отмена записи применяют тот же порядок. Отправленные задания не
дублируются, thank-you не рассылается всей исторической базе. Audit failure откатывает
настройку и очередь. UI не теряет черновик другой карточки или несохранённый текст
при простом переключении enabled.

Граница: уже начавшийся внешний HTTP/SMTP вызов невозможно отозвать транзакцией БД.
Поздний ответ помечается как acknowledged-after-revocation; это не обещание exactly-once
у внешнего провайдера. Проверки используют mocks, реальная доставка не сертифицирована.

### 6. Личные уведомления

`notification-preferences?business=…&user=me` → NotificationPreference
(Business, User, Category, in_app_enabled) → существующий
[routing filter](../../apps/notifications/routing.py).
VIEW нужен для чтения, UPDATE — для переключателя, backend дополнительно применяет scope.

Sales, tasks, outreach, ai_alerts, system, finance — существующие категории.
Отсутствие записи означает включённые обычные уведомления. Отключение влияет на
NORMAL; HIGH/URGENT сохраняют утверждённый обход предпочтений. Фильтр применяется
к role-based producers, задачам, переназначению, заявкам, входящему Inbox, внутренним
уведомлениям по записи. Это не отключение внешних сообщений клиентам, AI-движка
или уже отправленных уведомлений. Настройки другого пользователя/Business не влияют.

### 8. Подписка

`billing/current-subscription`, `/settings/`, `/change-plan/` → Subscription.
VIEW — чтение; MANAGE — запись. Все чтения и изменения используют явный selector
и фактические права выбранного бизнеса, включая аккаунт с несколькими Business.

| Параметр/действие | Решение |
| --- | --- |
| Текущий план/статус | Состояние сохранённой записи; не доказательство оплаты или работающего billing provider |
| Billing email | Отдельный контакт подписки, серверная email-валидация |
| Invoice name/tax ID/address | Отдельные реквизиты Subscription; не дополняются автоматически реквизитами Business |
| Payment method | Сохранённое справочное значение, только чтение |
| Выбор плана | Сохраняет requested_plan и время; UI прямо называет это предпочтением, без обещания смены активного плана/счёта |
| Pause/resume/cancel | Убраны из merchant UI: старый API меняет только metadata и не останавливает CRM/списания; API совместимость сохранена |
| Цена/платежи | UI не придумывает валюту, провайдера оплаты или коммерческие обязательства |

Запись metadata атомарна с audit только имён изменённых полей, без реквизитов в логе.
Новые коммерческие правила, квоты, платежи, блокировка CRM не создавались.

### 9. Использование

`billing/entitlements?business=…` → существующие limits + реальный usage:

| Метрика | Источник/период/единица |
| --- | --- |
| Users | Активные memberships, текущее количество |
| Bots | Существующие агенты, текущее количество |
| Automations | Правила, текущее количество |
| Storage | FileAttachment size, текущий объём в MiB |
| AI calls / messages / conversations | UsageCounter текущего календарного месяца, подписанный период |

`null` limit — без ограничения, ноль не превращается в infinity. Нет декоративного
процента заполнения при unlimited. Исходные лимиты/политика не менялись. Usage summary
также использует реальные текущие users/storage вместо месячного счётчика users.

### 10. Дополнительные поля

`custom-fields` → CustomFieldDefinition; `custom-field-values`/`bulk-upsert` →
CustomFieldValue → CRM card. Реализация: [views](../../apps/core/custom_field_views.py),
[validation/access](../../apps/core/custom_fields.py),
[typed card form](../../frontend/src/components/crm/drawers/panels.tsx).

| Параметр/действие | Семантика и ограничение |
| --- | --- |
| Entity | client/lead/deal/appointment; значения требуют существующей записи того же Business |
| Label / key | Label показывается в карточке; key ASCII, для не-ASCII названия создаётся допустимый ключ |
| Field type | text/textarea/number/money/date/datetime/select/multiselect/boolean/phone/email/url; сервер проверяет соответствующий JSON-тип |
| Options | Только выбор; уникальные непустые string values, поддержаны прежние объекты value/key/label |
| View/edit roles | Проверяемые membership roles, picker вместо неподконтрольной строки; пустой список означает все роли в пределах прав на сущность |
| Required flag | Справочно, только чтение UI: сам флаг не блокирует сохранение CRM; правила required fields стадии остаются отдельным работающим механизмом |
| Active | Определяет появление в карточке и возможность записи новых значений |
| Sort order | Порядок определения/значений |
| Изменение/удаление | При сохранённых значениях identity/type не меняются, несовместимое удаление option отклоняется; вместо удаления определения предлагается отключение |
| Значения карточки | Отправляются лишь изменённые и разрешённые поля; multiselect — массив, boolean — JSON boolean, пустое значение не превращается самопроизвольно в false |

Управление определениями требует settings:update. Чтение значений пересекает
settings:view, доступ/область CRM-объекта и view_roles. Bulk edit дополнительно
требует UPDATE CRM-объекта, edit_roles и active; одиночный CRUD сохраняет свои
settings permissions и те же объектные ограничения. Identity значения неизменна.
Неверное значение/ошибка audit откатывает весь batch. Деактивация сохраняет историю.
