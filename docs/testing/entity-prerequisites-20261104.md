# Зависимости сущностей и подготовка к созданию — 04.11.2026

## Назначение и границы

По поручению владельца сохранён разбор: какие пользовательские сущности связаны
между собой, что необходимо подготовить для создания и как объяснять отсутствие
зависимостей. Исходный пример: при отсутствии услуг и специалистов окно новой
записи должно направлять пользователя к настройке бизнеса, а не предлагать
заполнение заведомо неработающей формы.

Это аналитический срез, роль **evidence**, а не новый контракт, roadmap или
разрешение реализации. Требования определяют [CRM](../current/crm.md),
[доступ](../current/access.md), [frontend](../current/frontend.md),
[AI](../current/ai.md) и [интеграции](../current/integrations.md).
Столбцы «Подсказка / следующий шаг» ниже — предлагаемое поведение, если прямо
не указано, что оно уже присутствует. Они не являются готовыми i18n-текстами.

Срез: канонический PlatformaCRM, ветка `codex/ui-testing-toolkit`, HEAD
`66101d509cb7642b2928275e48c4b64354abf07b` **плюс незакоммиченные изменения**.
Поэтому HEAD отдельно не воспроизводит рассмотренную реализацию. Проверены
модели, serializers, доменные проверки, формы, маршруты и существующие тестовые
сценарии. Полный браузерный/API-прогон создания всех сущностей не выполнялся;
это не сертификация работоспособности и не утверждение о deployment.
Основной подробный trace относится к CRM/записи/филиалам; дополнительные модули
в матрице отражают обзор их моделей, форм и проверок запуска, без полного
покрытия всех провайдеров и альтернативных entry points.

Охвачены пользовательские сущности CRM и её настройки. Служебные журналы,
BusinessEvent, delivery attempts, результаты AI и системные счётчики не требуют
самостоятельного пользовательского онбординга. Коммерческие сущности платформы
и внутреннее администрирование не сертифицированы этим анализом.

## Общая модель зависимостей

Для каждой операции нужны выбранный Business, доступный модуль и право на
действие. Все связанные объекты должны быть доступны пользователю и принадлежать
тому же бизнесу. Отсутствие прав нельзя представлять как пустой справочник.

Различать:

1. **Настройку бизнеса**: услуга, специалист, расписание, назначение в филиал.
2. **Данные операции**: клиент, сумма, дата, выбранная услуга.
3. **Текущую доступность**: свободный слот, активность, отсутствие пересечений.
4. **Готовность к запуску**: канал, получатели, действия автоматизации. Черновик
   часто можно сохранить раньше, чем выполнить внешнее действие.

Пустой справочник не всегда блокер: задача не требует клиента; услуга не требует
специалиста; общий график не требует сотрудника; черновик рассылки не требует
готовой очереди получателей. Специалист и аккаунт сотрудника CRM — разные сущности.

## Матрица: базовые сущности и настройка бизнеса

| Сущность / настройка | Обязательные зависимости и граница | Подсказка / следующий шаг |
| --- | --- | --- |
| Клиент | Бизнес и имя; услуги, график и филиал не нужны. Телефон/email сейчас необязательны | Сразу форма клиента |
| Услуга | Название, длительность; цена может отсутствовать | Сразу форма услуги |
| Специалист | Карточка ресурса типа staff; аккаунт для входа необязателен | Создать карточку, затем настроить работу |
| Оборудование / рабочее место | Карточка ресурса соответствующего типа | Не считать оборудование специалистом для записи |
| Сотрудник с доступом в CRM | Учётная запись/приглашение и роль; контакты зависят от способа приглашения | Настройка доступа, без обязательного создания специалиста |
| Роль | Business и разрешения | Можно подготовить до приглашения сотрудников |
| Команда | Business и название; для добавления участников — сотрудники | Можно создать пустую команду |
| Филиал | Business и название | Создать, затем подготовить услуги, назначения и график |
| Общий график бизнеса | Business | Можно настроить без специалиста |
| Персональный график | Существующий специалист | Сначала добавить/выбрать специалиста |
| Исключение графика / отсутствие | Специалист и дата/период; филиал зависит от сценария | Перейти к нужному специалисту и его расписанию |
| Услуга филиала | Филиал и услуга общего каталога | При пустом каталоге сначала создать услугу |
| Назначение специалиста в филиал | Филиал, специалист; для записи также услуги филиала, назначенные специалисту | Подготовить услуги и назначение; пустое назначение не доказывает готовность к записи |
| График специалиста в филиале | Предварительное активное назначение специалиста в филиал | Сначала назначить специалиста, затем настроить интервалы |
| Перемещение между филиалами | Два разных филиала и время перемещения | Не требовать при единственном филиале |

| Этап плана | Активная услуга; специалист и филиал могут быть назначены позже | При отсутствии услуг — переход к их настройке |

| Платёж | Клиент, сумма, валюта, дата и способ оплаты; сделка/запись необязательны | Выбрать/добавить клиента; не требовать запись для самостоятельного платежа |
| Возврат | Исходный платёж, доступный остаток и причина | Объяснить отсутствие исходного платежа или доступной суммы |
| Заметка / комментарий | Доступный контекст, если создаётся в карточке объекта | Не отправлять на общую настройку бизнеса |
| Вложение | Разрешённый контекст и допустимый файл | Ошибка файла/доступа непосредственно в загрузке |

Единственный доступный филиал автоматически выбирается в `useBranchBooking`;
выбор между несколькими нужен только при реальной альтернативе. Это не отменяет
проверки активности, доступа, услуг и расписания. Backend также умеет разрешать
единственный активный филиал, но число доступных пользователю и число активных
филиалов бизнеса — разные множества.

Без филиалов персональные часы могут заменять общий график. В филиальном режиме
используется пересечение часов филиала и специалиста. Поэтому единый совет
«добавьте общий график» неверен для всех сценариев. Создание первого филиала
также имеет отдельную [логику переноса существующих настроек](../../apps/branches/compatibility.py);
это не повод автоматически создавать филиал при подготовке записи.

## Найденные несогласованности

1. **Общей проверки готовности операции нет.**
   [Онбординг](../../apps/onboarding/services.py) считает любой активный ресурс
   и любую строку WorkingHours достаточными для соответствующих шагов. Оборудование
   не является специалистом, выходной не даёт слотов, филиальный ScheduleDay
   отличается от WorkingHours. Наличие connector также не доказывает соединение.
   Этот checklist нельзя использовать как разрешение создания записи.
2. **Сообщение о филиалах смешивает причины.**
   [useBranchBooking](../../frontend/src/hooks/useBranchBooking.ts) отбирает
   can_book/active/nonarchived. В [AppointmentForm](../../frontend/src/components/forms/AppointmentForm.tsx)
   отсутствие доступных филиалов перекрывает дальнейшие подсказки услуг/специалистов.
   По одному сообщению нельзя установить, причина в правах, активности или настройке.
   Фактическая причина состояния бизнеса на пользовательском скриншоте отдельно
   не устанавливалась запросом его данных.
3. **График не входит в needsSetup формы записи.** Возможна полная форма с
   последующим no-slots. Нужно различать отсутствующую настройку, выходной,
   занятость и неподходящую длительность. Нельзя каждый пустой день считать
   ненастроенным бизнесом.
4. **Клиент обязателен, путь создания непоследователен.** В recordFirst-форме
   AppointmentForm клиент выбирается через ClientPicker без createAction.
   В [LeadForm](../../frontend/src/components/forms/LeadForm.tsx) такое действие есть.
   [PaymentEntityPicker](../../frontend/src/features/payments/PaymentEntityPicker.tsx)
   при пустом результате также показывает noMatches без создания клиента.
5. **Ссылки настройки недостаточно точны и неравномерно учитывают права.**
   В филиальном режиме ссылки услуг/специалистов из AppointmentForm не передают
   section. [BranchEditor](../../frontend/src/features/business/components/BranchEditor.tsx)
   поддерживает section, но по умолчанию открывает details. SetupNotice для
   услуг/специалистов не проверяет canManageSchedule, в отличие от ссылки филиала.
6. **План визитов не объясняет отсутствующие зависимости.**
   [PlanEditor](../../frontend/src/features/calendar/PlanEditor.tsx) показывает
   пустой список услуг и disabled Save, не предлагает настройку или создание клиента.
   Поле филиала показывается при любом ненулевом числе филиалов. Сервер допускает
   пустой план, UI начинает с обязательного этапа: это различие сценариев, которое
   нужно согласовать, а не молча менять контракт.
7. **Внутри настройки тоже возможен тупик.**
   [BranchCatalogEditor](../../frontend/src/features/business/components/BranchCatalogEditor.tsx)
   при пустых каталогах предлагает селекторы/disabled Save без перехода к созданию
   услуги или специалиста. [Сделки](../../frontend/src/features/deals/DealsPage.tsx)
   при отсутствии воронки показывают ошибку без действия настройки.

Это результаты статического анализа, не список выполненных исправлений и не
новая очередь разработки. Наличие серверной проверки не доказывает удобство
UI; наличие UI-подсказки не доказывает защиту API.

## Предлагаемый пользовательский сценарий

Для создания записи без услуг и специалистов: окно «Настройте бизнес для создания
записи», список только фактически недостающих шагов и действие перехода в
[существующий раздел Бизнес](../../frontend/src/features/business/components/BusinessWorkspaceNav.tsx).
Направление владельца — использовать этот раздел с вкладками. Точные тексты,
общий компонент и API готовности здесь не реализованы и не утверждены как контракт.

Условия должны различаться:

- Нет настройки → конкретная вкладка бизнеса с нужным филиалом/специалистом.
- Нет связанной сущности → выбор или создание клиента/другого объекта.
- Нет прав → объяснение необходимости помощи администратора, без недоступного CTA.
- Настройка есть, но нет доступности → другая дата/специалист/филиал.
- Ошибка загрузки → повтор загрузки, а не утверждение «нет услуг».
- Черновик разрешён → сохранить черновик, проверять готовность перед запуском.

Для будущей реализации нужен проверяемый результат на сценариях: пустой бизнес;
услуги без специалистов; оборудование без staff; отсутствие графика; корректный
график без свободных слотов; ноль/один/несколько филиалов; отсутствующее назначение
услуги специалисту; отсутствие доступа; ошибка API; восстановление после настройки.
Переход к настройке должен сохранять или явно восстанавливать исходный контекст
создания. Это предлагаемые критерии, а не выполненные тесты.
