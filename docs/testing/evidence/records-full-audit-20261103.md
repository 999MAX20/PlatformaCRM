## Подтверждённые дефекты

### RF-01 · P2 · TEAM-доступ разрешён сервером, но карточка скрывает действия

Роль с `appointments.update=team`, в команде которой находится связанный со
специалистом пользователь, открывает запись #7. Backend `can(...UPDATE,obj=record)`
возвращает `allowed=True`; карточка не показывает ни одного
`data-appointment-action-id`. У owner на той же записи действия есть.
[Снимок роли TEAM](records-full-audit-20261103-assets/team.png).

Причина: [appointmentAccess.ts](../../../frontend/src/features/calendar/appointmentAccess.ts),
строки 27–28: после `business` принимается только `own`. Этот же результат
управляет readOnly вложений карточки. Это отказ в разрешённой работе, не обход прав.

Минимально: согласовать клиентскую доступность с backend object capabilities,
сохраняя branch guards. Проверить business/own/team/denied, смену роли и филиал;
скрытие кнопок не должно заменять серверную проверку.

### RF-02 · P2 · «Назад» из карточки теряет контекст списка

Открыть `?from=2026-12-15&to=2026-12-15&search=Audit&page=2`: 11 результатов.
Открыть строку, нажать кнопку «Назад» в карточке: отображается первая страница
общей выборки, `search` и `page` исчезли. Период восстанавливается отдельно.
Browser Back не смешивается с этой кнопкой: дефект именно явного возврата карточки.

[AppointmentWorkspacePage.tsx](../../../frontend/src/features/calendar/AppointmentWorkspacePage.tsx),
строка 208: безусловный `navigate('/app/appointments')`;
[RecordsTable.tsx](../../../frontend/src/features/calendar/RecordsTable.tsx) не передаёт return context.
Пользователь повторно настраивает выборку после обработки каждой записи.

Минимально: передавать проверенный локальный return URL/context и сохранять поиск,
статус, фильтры, сортировку и страницу. Для прямой ссылки оставить безопасный fallback.
Проверить список → карточка → Назад и переходы из календаря/плана/Клиента.

### RF-03 · P2 · Закрытие формы во время сохранения не останавливает поздний переход

Выбрать клиента/услугу/специалиста/слот, отправить создание, задержать ответ API,
нажать Escape. Форма закрывается. После успешного ответа открывается новая карточка,
хотя пользователь уже вернулся к списку. Реальный POST на изолированной БД создал
одну запись; [receipt перехода](records-full-audit-20261103-assets/late-create.json).
Повтор после временного 503 сохраняет idempotency key — дублирование этим тестом
не установлено.

[RecordsPage.tsx](../../../frontend/src/features/calendar/RecordsPage.tsx),
`closeCreate`, `create.onSuccess` и Modal (строки 66–86, 103): close не учитывает pending,
успех всегда выполняет navigate. Аналогичный close переносa следует проверить при исправлении.

Минимально: явное поведение pending — удерживать форму до результата либо сохранять
видимый статус операции и исключить неожиданный переход после закрытия. Проверить
Escape/крестик/переход, успех/ошибку/неизвестный исход; не менять серверную идемпотентность.

### RF-04 · P2 · Несуществующая страница превращается в неисправимую кнопку «Повторить»

`?from=2026-12-15&to=2026-12-15&page=999` → workspace 404.
«Повторить» снова отправляет `page=999` и получает 404. Номер страницы не исправляется,
пагинация исчезает; общий сброс теряет все условия. Это также риск для старой ссылки
или последней страницы после уменьшения выборки.
[Экран ошибки](records-full-audit-20261103-assets/invalid-page.png).

[RecordsPage.tsx](../../../frontend/src/features/calendar/RecordsPage.tsx), строки 98–102:
ошибка workspace передаётся в общий read-error с `records.refetch()`.
Минимально: распознавать недопустимую страницу и предложить/выполнить возврат на первую
с сохранением остальных условий. Настоящие network/permission ошибки не маскировать.

### RF-05 · P2 · Поиск записывает каждую букву в историю браузера

Ввести `Audit` с интервалом 180 мс: минимум пять workspace-запросов;
Browser Back меняет поле на `Audi`, вместо возврата к предыдущему осмысленному состоянию.
В исходниках каждый onChange меняет URL; для нового query нет previous-data placeholder.
При медленном API это также заменяет таблицу состоянием первоначальной загрузки.
Количество запросов проверено, production latency не измерялась.

[RecordsToolbar.tsx](../../../frontend/src/features/calendar/RecordsToolbar.tsx), строка 54;
[RecordsPage.tsx](../../../frontend/src/features/calendar/RecordsPage.tsx), query и isPending.
Минимально: локальный draft + debounce, replace для промежуточного текста, сохранение
последнего результата с обозначением обновления. Проверить очистку, быстрый ввод,
устаревший ответ, Back/Forward и сброс страницы.

доступный выбор даты/специалиста и корректное обращение к ответственному за расписание.
Проверить роль creator и управляющего графиком, включая ошибку чтения расписания.
