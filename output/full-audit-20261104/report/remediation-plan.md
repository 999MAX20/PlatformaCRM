# Порядок устранения

Это предложение по результатам аудита, а не разрешение менять продукт, публиковать
его или начинать все этапы. Точные finding IDs, зависимости и приёмка сохранены
в [remediation-groups.json](../remediation-groups.json). Все87 канонических ID
включены ровно в одну группу; UI14 сохранена как alias ATTACHMENT-RETRY.
[Сверка связей](../remediation-mapping-validation.json) не заменяет приёмку исправлений.

Сначала устранить обходы исходных прав в аналитике и риск попадания приватных
данных в архивы/логи. Затем укрепить атомарность и владение попыткой: audit rollback,
idempotency prune, stale workers, повтор частичной загрузки. Эти механизмы нужны
для надёжной фоновой работы, рассылок и CRM-переходов.

Следующие независимые направления — полнота очередей/consumers и продвижение
batch scans; согласованность бронирования/эффектов создания; входная валидация и
pagination. Для каждого изменения нужны positive и negative controls, сохранение
данных при ошибке и только относящиеся проверки. Прогон, ожидающий известный дефект,
не является acceptance исправления.

Стоимость Clients и карточек снижать после фиксации permission invariants.
Сравнение должно использовать те же распределения данных, SQL/payload budgets,
concurrency и timeout boundary. Результат Windows-прогона не задаёт размер облака.

Web-находки исправлять по достижимым сценариям: recovery, сохранение черновика,
полнота списков, keyboard/focus и локализация. Общая замена компонентов без
доказанного общего влияния не требуется. При изменении shared-контракта проверить
репрезентативных потребителей, а не только экран исходного дефекта.

REQ01/REQ02 — отдельная реализация уже открытых требований. Нужны только реально
незакрытые money/audio решения; существующие решения повторно не согласовываются.
REQ04 и исторический native сохраняют собственные границы. Отсутствие native
устройства не разрешает объявить текущий web неисправным из-за исторического кода.

Тестовые fixtures, runbooks и docs исправлять вместе с затронутым поведением.
Старые failures не удалять из истории и не переименовывать в PASS. Перед допуском
нужны exact-candidate release checks и отдельно разрешённая проверка целевой среды;
этот аудит deployment не выполняет.
