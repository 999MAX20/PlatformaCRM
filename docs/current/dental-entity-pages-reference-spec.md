# Стоматология: страницы клиента и записи по референсам

Источник: поручение владельца 24.11.2026 в side conversation. Связанный план:
[DENTAL-MCS-20261122](../testing/task-state/DENTAL-MCS-20261122.md).

## 1. Статус и границы

Этот документ задаёт новую реализацию интерфейса. После просмотра макетов владелец
поручил реализацию страницы записи, затем отдельно страницы клиента по exec-0c447717. Клиент восстановлен по этому референсу.
Описание компонентов ниже принято как направление реализации; роли не меняются.
Раздел 9 содержит анализ и рекомендации, не разрешение изменить security policy.

Маршруты: `/app/clients/:id`, `/app/appointments/:id` и их существующие alias-входы.
Страница клиента монтирует обзор, медкарту, визиты, существующие документы/вложения и оплату по правам.
Страница записи восстановлена в рамках текущего этапа: осмотр, одонтограмма,
таблица выполненного лечения, план, рекомендации и контекст визита. Общие
header/sidebar, авторизация и route guards сохраняются. Списки и календарь
не очищались. Прежняя логика и сервисы переиспользуются.

Целевая композиция применяется в стоматологическом модуле. Общий CRM и его
отраслевая нейтральность сохраняются; при восстановлении немедицинского бизнеса
используется административный вариант с прежними разрешёнными функциями.

Документы, шаблоны, ЭЦП, бот, полный архив и закупки остаются на паузе. Наличие
этих элементов на референсе не возобновляет их разработку. Они исключаются из
текущего функционального варианта без пустых карточек и неработающих кнопок.
Пауза относится к новой разработке этих механизмов: существующая вкладка документов на странице клиента сохранена с прежними правами.

не источник данных пациентов. Исходные файлы скопированы в постоянные design-assets
проекта без изменения изображения. В этой задаче они
не генерируются и не заменяются. Для отсутствующих ассетов нельзя обещать точное
совпадение рисунка зубов: сначала сверить существующий atlas с эталоном.

Контрольный desktop: viewport 1536×1024 CSS px, zoom100%, DPR1, светлая тема,
русский язык, загруженный шрифт. Сначала сравнивать при одинаковом viewport,
затем проверять адаптивность; уменьшение масштаба браузера не исправляет вёрстку.

Визуальные отличия допустимы только для реальных данных, разрешений, отложенных
документов и согласованной медицинской легенды. Их перечислить в evidence.
Нельзя объявить совпадение по одной похожей цветовой палитре или сборке PASS.
Числа ниже являются измерительными ориентирами по растру; финальные значения
уточняются наложением скриншотов. Не менять глобальную типографику ради двух страниц.

## 4. Клиент: структура и действия

1. Breadcrumb «Клиенты / имя», возврат к списку с сохранением фильтров/страницы.
2. Header: avatar72px, имя, номер медицинской карты; справа редактирование и запись.
   ID клиента не выдавать за номер медкарты. Если номера нет, честное пустое значение.
3. Tabs одной строкой: Обзор, Медкарта, Визиты, Документы, Оплата. Новая разработка документов отложена; существующий workspace переиспользован.
   Дополнительные общие функции не добавлять самостоятельными вкладками в этом виде;
   существующие заметки/задачи/вложения при возвращении функций разместить в
   соответствующей вкладке/меню, без потери данных и без возобновления документов.
4. Обзор слева: аллергии → следующий приём → последние визиты → медицинская сводка.
5. Справа одна компактная панель: контакты, дата рождения/возраст, канал связи,
   затем заметки. Не добавлять большие пустые разделы, теги и архивные кнопки в обзор.

| Блок | Данные / поведение | Пустота / ограничение |
| --- | --- | --- |
| Аллергии | Последнее сохранённое состояние пациента, заметный баннер≈60px при наличии | Не путать «не заполнено», «нет аллергий» и «нет права читать» |
| Следующий приём | Ближайший актуальный будущий визит; начало–конец, врач, услуга; открыть запись | Компактное предложение записать; никаких выдуманных дат |
| Последние визиты | Завершённые визиты, дата, врач, выполненное лечение/результат; последние3–5 строк | Ссылка на все визиты; клинический результат только при разрешении |
| Медицинская карта | Активные диагнозы, краткий план, время последнего изменения, мини-одонтограмма | Сначала сервер определяет доступный контекст; без него клиническая сводка не запрашивается |
| Контакты | Реальный телефон, DOB, вычисленный возраст, предпочтительный канал | Не подменять отсутствие DOB email; неизвестное поле компактно опускать |
| Заметки | Общие клиентские заметки и разрешённое редактирование | Общие заметки не должны обходить ограничение клинических данных |

Медицинская сводка привязана к пациенту, не к случайному первому приёму. Отсутствие
будущей записи не должно скрывать уже существующую карту. Если нет подходящего
patient-summary API, это отдельный функциональный gap, а не повод рисовать заглушку.
Мини-одонтограмма показывает последнее сохранённое наблюдение каждого зуба; нажатие открывает Медкарту. Поверхности и история доступны в полной карте. Связанный канал показан только при наличии идентификатора; предпочтительный канал модель клиента пока не хранит. В последних визитах показывается фактическая услуга, а не выдуманное клиническое заключение.
На вкладке Медкарта доступна полная одонтограмма, наблюдения/история и план лечения.
Набор медицинских данных и действия ограничены эффективными правами пользователя.

## 5. Запись: структура и действия

Header: breadcrumb, возврат, имя пациента, ссылка на карту рядом с именем;
вторая строка дата, интервал, врач, кабинет. Справа статус, перенос, меню, сохранить.
Вкладки текущего объёма: Приём, История. Отложенные Документы не отображать.
Не смешивать историю изменений записи и историю медицинских осмотров без подзаголовков.

Левая колонка:

- Единый блок «Осмотр»: жалобы одной компактной строкой, расширяемой при длинном вводе.
- Ниже одонтограмма и инспектор выбранного зуба в одной горизонтальной композиции.
- Затем «Выполненное лечение» с таблицей, не общим textarea.
- Затем рекомендации; план лечения отдельной понятной частью сценария, не сваливать
  таблицу планируемых и выполненных услуг в один неразличимый список.
- Анамнез, противопоказания, объективные данные и прочие существующие поля доступны
  через компактное раскрытие дополнительных полей. Их значения не теряются.

Правая колонка:

- Карточка «Визит»: услуга, врач, интервал, кабинет, состояние сохранения.
- Одно основное действие «Завершить приём»; после завершения «Повторная запись».
- Перенос остаётся в header, отмена/неявка и второстепенные команды в меню.
- Карточка документа на референсе исключена из текущего scope, свободное место
  не заполнять иной декоративной карточкой и не растягивать блок «Визит».

Контрольные позиции референса: начало «Осмотра» y≈276, одонтограмма y≈412–738,
выполненное лечение y≈754–900, рекомендации y≈914–1010. При эталонной длине текста
основной процесс должен помещаться примерно в один viewport. Длинные реальные
данные могут увеличивать высоту: запрещено обрезать смысл ради совпадения картинки.

Сохранение использует существующие сервисы/version guards. Не дублировать Save в
каждом блоке. Индикатор «Сохранено» только после ответа сервера. Ошибка сохраняет
ввод и даёт повторить; конфликт версии требует сверки, не молчаливой перезаписи.
Завершение использует текущий clinical transition и ограничения обязательных данных.
Пауза документов не является разрешением обойти обязательные документы конкретного
приёма. При имеющемся требовании показать точную причину блокировки.
После завершения открыть повторную запись с пациентом/филиалом, датой по выбору,
без дублирования прежнего завершённого визита. Возврат не теряет план лечения.

## 6. Одонтограмма и лечение

- На desktop при ширине1536 схема≈700px и инспектор≈300px, gap12–16px.
  Не ждать viewport1400+, если в основной колонке уже хватает места: ориентироваться
  на фактическую ширину контейнера. Уменьшение viewport не должно превращать её в
  многометровую форму с пустым пространством.
- Два ряда постоянных зубов с корректными FDI:18…11,21…28 и48…41,31…38.
  Не копировать ошибочную подпись диапазона1–18 с макета. Детская формула сохраняется
  из существующей реализации с корректными номерами, отдельный компактный переключатель.
- Иллюстрации одинакового визуального масштаба с сохранёнными пропорциями;
  выбранный зуб имеет явный контур, номер и доступное имя. Статус не передаётся
  одним цветом: текст/символ и легенда обязательны.
- Согласованные состояния: Не осмотрен; Осмотрен — без отмеченных изменений;
  Есть наблюдение; Зуб отсутствует. Запись без состояния не считается здоровой.
- «Кариес / пломба» на картинке не превращаются автоматически в новые серверные
  состояния и шкалу тяжести. Для отдельной диагностической раскраски сначала
  определить справочник и mapping; это открытое медицинское решение.
- Инспектор: номер зуба, предыдущее/следующее, сохранённое состояние, наблюдение,
  диагноз при наличии утверждённого поля, комментарий, добавить лечение.
  Не заменять наблюдение диагнозом без соответствующего контракта данных.
- При смене зуба несохранённый ввод сохраняется в черновике либо запрашивается
  решение; нельзя silently discard. Показать прежнюю историю и автора/дату изменения.
- Таблица лечения: услуга/манипуляция, зуб, описание, длительность, статус, меню.
  «Добавить позицию» открывает короткую форму. Номер зуба из инспектора предзаполнен.
  Услуги берутся из каталога клиники; клиника свободно ведёт свой список услуг.
- Планируемая манипуляция не считается выполненной. Для перехода в выполненную
  требуется явное действие. Свободный исторический текст сохраняется; запрещено
  автоматически выдавать его за структурированные медицинские процедуры.

## 7. Формы, адаптивность и состояния

Редактирование клиента, перенос, добавление лечения и повторная запись используют
короткие dialogs/drawers. Содержимое всей карточки в модальное окно не возвращать.
У каждого поля видимый label; Escape закрывает с проверкой dirty, фокус возвращается
на кнопку. Повторный submit не дублирует запись; ошибка не обнуляет поля.

Desktop1536 и1366: две колонки при достаточной ширине. Tablet1024: инспектор можно
переносить под схему, блок визита компактно перестраивается; сохраняется порядок
«контекст → осмотр → лечение → завершение». Mobile390 и360: одна колонка, отступ16px,
H1≈24px, текст14–16px, touch44px; toolbar переносится без наезда. Вкладки скроллятся
локально, страница не имеет горизонтального overflow. Зубные ряды допускают собственный
горизонтальный scroll с видимым указанием продолжения; не уменьшать зубы до непопадаемых
точек. Редактор зуба открывается снизу/в drawer, таблица лечения становится списком
с теми же данными. Фиксированные действия не закрывают последние строки/клавиатуру.

Loading сохраняет геометрию блока. Empty означает отсутствие данных, Forbidden
означает отсутствие полномочия, Error означает сбой: эти состояния не взаимозаменяемы.
403 не должен молча сносить все клинические вкладки после их показа. Чужой Business
не раскрывается через название/счётчик/summary. При переключении клиники очищаются
прежние данные и учитываются новые права. Проверить RU/KK/EN и длинные имена.

## 8. Переиспользование и реализация по этапам

Сохранённые ClientWorkspacePage/AppointmentWorkspacePage содержат API-hooks,
navigation context, permissions, dirty guards. Переиспользовать ClientForm,
AppointmentRescheduleForm, ClinicalAppointmentEntry, ToothChart/ToothShape,
clinical plan booking, существующие frontend/src/api клиенты. Не возвращать
прежнюю вложенную композицию ради повторного использования логики.

| Этап | Завершённый результат | Локальная проверка |
| --- | --- | --- |
| A | Восстановленная клиентская страница, реальные контакты/следующий визит/история/summary/мини-схема | Один пациент с историей и один пустой; desktop/mobile, открытие и возврат |
| B | Приём: осмотр, интерактивная одонтограмма и зубной редактор по геометрии эталона | Выбрать зуб, сохранить наблюдение, сменить и открыть снова; ошибка сохраняет ввод |
| C | План/выполненное лечение, рекомендации, завершение и повторная запись | Один связанный сценарий от записи до следующего визита; не дублируются сущности |
| D | Визуальная сверка и ролевые состояния двух страниц | Наложение эталонов, doctor/head/owner/reception, точечные fixes, итоговый build/types |

Ролевое переустройство отдельно, после утверждения §9; не блокировать геометрию
и уже разрешённые рабочие сценарии ожиданием этого решения. API gaps закрывать
только в необходимом для строки таблицы объёме, без переписывания готового ядра.

Для сравнений подготовить изолированные детерминированные synthetic данные,
сходные по длине с эталоном. Не записывать их в рабочую БД. Снять обе страницы
1536×1024 и390px, составить overlay/diff; проверить header, tabs, границы колонок,
одонтограмму, таблицу и действия. Целевой геометрический допуск≈4px для ключевых
границ при одинаковых данных; текст/иконки сравниваются визуально с учётом raster
antialiasing. Утверждение «1 в1» допустимо только после осмотра, не по проценту diff
или passing-tests. Разрешённые расхождения из §2 подписать отдельно.

Не запускать CI, полный backend и большой E2E ради вёрстки. После согласованного
UI-среза один build/types; точечные тесты интеракций/прав. Если меняется серверный
контракт: focused happy/invalid/role/tenant/version tests. Существующие зелёные
проверки не повторять при неизменных inputs. Успешный build не равен UI acceptance.

## 9. Роли и регистрация: анализ, без изменений кода

### Подтверждённое текущее поведение

`apps/medical/role_access.py::assert_medical_role_permission` требует активную
MedicalRoleAssignment и отдельный RolePermission. Владелец Business не является
медицинской ролью автоматически. Назначение самому себе отвергается также в
`apps/medical/role_services.py::assign_medical_role` и при чтении назначения.
Филиальные права и основание доступа к пациенту/приёму проверяются дополнительно.
Это объясняет типичный сценарий нового владельца, но конкретная сессия пользователя
и её API-ответы не исследованы: иные причины403/ошибки БД не исключены.

Нынешний UI местами решает, показывать ли клинический блок, по включённому модулю,
а не по эффективным полномочиям. Результат: обещание доступа во вкладке, затем отказ
или исчезновение содержимого. Это отдельный UX-gap даже при корректном отказе API.

### Рекомендуемая модель

Разделить три понятия: личный аккаунт; полномочия управлять рабочим пространством
клиники; профессиональная роль в медицине. Пользователь может совмещать роли.
«Создал аккаунт» не означает «главврач» и не даёт доступа к другой клинике.

Требование владельца: медруководитель/главврач должен видеть100% информации CRM
своей клиники. Зафиксировано как новое требование к будущей модели. Рекомендую
готовый профиль «Руководитель клиники / главврач»: вся информация всех филиалов
этой клиники, включая CRM, пациентов, медицинскую историю и управленческие разделы.
Просмотр всей информации не означает чтение паролей/ключей, чужих Business,
право менять автора подписанного документа или уничтожать audit. Полный просмотр
и полномочия изменять/выдавать права/экспортировать настраиваются отдельно.

| Профиль | Просмотр по умолчанию | Основные действия |
| --- | --- | --- |
| Руководитель клиники / главврач | Вся бизнес- и медицинская информация своей клиники, все филиалы | Управление клинической работой; административные полномочия согласно совмещённому профилю |
| Владелец без медицинских обязанностей | Управленческие, финансовые и административные данные | Команда/доступы/настройки; медицинский доступ только явным назначением |
| Врач | Назначенные пациенты/приёмы в разрешённых филиалах | Осмотр, зубы, план, лечение, завершение собственных разрешённых приёмов |
| Ассистент | Приёмы с назначенным участием | Помощь/черновики в согласованной матрице; без самостоятельного завершения от лица врача |
| Ресепшен | Контакты, расписание, разрешённые административные данные | Запись, перенос, повторная запись; без произвольного чтения осмотра |

Если клинике нужен медруководитель без финансового доступа, отдельный настраиваемый
профиль «Медицинский руководитель» с полным клиническим просмотром; не менять смысл
полного профиля «Руководитель клиники / главврач» незаметным урезанием.

### Регистрация

1. Первый выбор: «Создать пространство клиники» или «Присоединиться к клинике».
   Отрасль сейчас только «Стоматология», сервер включает медицинский модуль.
2. При создании: «Руководитель / главврач», «Владелец без медицинских обязанностей»,
   «Настраиваю по поручению руководителя». Объяснить итоговые права рядом с выбором.
3. Для руководителя новой пустой клиники предложить совмещённый управленческий и
   медицинский профиль. Нужен явный bootstrap-процесс первичного назначения с audit,
   а не глобальная отмена запрета самоназначения. Он применим только при создании
   нового Business, не при вступлении в чужую существующую клинику.
4. Настраивающий по поручению получает ограниченную setup-роль без медицинского
   чтения, приглашает реального руководителя. Передача административного контроля
   происходит после принятия приглашения; не повышать setup-сотрудника автоматически.
5. Сотрудник существующей клиники входит по приглашению. Выбор «я главврач» в форме
   выражает запрос, но не назначает роль. Роль/филиалы/срок приглашения задаёт
   уполномоченный администратор; сервер проверяет принадлежность и принятие.
6. Для уже созданного владельца отдельный экран настройки своей клиники: текущие
   полномочия, назначение руководителя, явный путь совмещения ролей после утверждения
   policy. Не создавать второй аккаунт как обязательный обход self-grant restriction.

Рекомендованный bootstrap меняет прежнее согласованное правило запрета
самоназначения. Сейчас он только предложение; до утверждения не писать миграцию,
не менять backend guards, не выдавать пользователю роль вручную и не расширять API.

### Настройки доступа

Единый раздел «Сотрудники и доступы»: человек → профили → филиалы → доступ к
пациентам → разрешённые действия. Presets плюс индивидуальные ограничения;
предпросмотр итоговых прав до сохранения. Для медицинских действий остаются
профессиональные ограничения, не всё можно включить произвольным checkbox.
Сочетание ролей должно иметь однозначное правило: разрешения объединяются,
явный индивидуальный запрет имеет приоритет; tenant и медицинские lifecycle
ограничения нельзя расширить ролью. Это предлагаемая семантика для согласования.

Показывать причину недоступности: нет роли, филиала, назначения или модуль отключён;
технический сбой отдельно. Предложить действие только уполномоченному пользователю:
настроить доступ или обратиться к администратору. Отозванные права применяются
сервером сразу, включая открытый экран; кеш очищается, несохранённый клинический
ввод не отправляется через прежние полномочия. История выдачи/отзыва с автором,
временем и причиной обязательна. Запретить удаление последнего администратора
без передачи полномочий. Нельзя показать секреты в предпросмотре доступа.

### Что ещё надо утвердить перед реализацией ролей

- Bootstrap для создателя новой клиники, совмещающего руководителя и главврача,
  и безопасный аналог для уже существующего единственного владельца.
- Право выдачи медицинских профилей: рекомендую владелец/уполномоченный руководитель;
  клинические назначения в пределах своих филиалов, без повышения за пределы своих прав.
- Матрица действий полного главврача: полный просмотр утверждён в этом поручении;
  массовый экспорт, финансы, передача владения и выдача прав согласовать отдельно.
- Правило объединения ролей/приоритета запретов и профиль setup-сотрудника.

Будущая приёмка: новый главврач открывает обе полные страницы; немедицинский владелец
видит административный вариант с понятной причиной; врачA не читает пациентаB;
ассистент и ресепшен не обходят запреты; приглашение не повышает права самовыбором;
отзыв/филиал/смена клиники/последний администратор проверяются локально на сервере.

## 10. Принятые макеты компонентов страницы записи

Основной новый эталон: [страница записи](assets/dental-reference/appointment-spec-preview-v1.png).
Листы компонентов расположены в `assets/dental-reference/appointment-components-v1/`.
Макеты приняты владельцем как визуальное направление: компактно, основные данные
на одном desktop-экране, подробный ввод в окнах. Общая оболочка CRM сохраняется:
выдуманные фоновые меню, пациенты и шапки листов не являются требованиями.

### Анализ изображений и обязательные поправки

- Листы хорошо задают форму/иерархию полей, footer с действиями и emerald-акцент.
  Их увеличенный масштаб нужен для чтения компонентов, не задаёт размер реальных окон.
- «Подтвердить» под статусом «В работе» на листе01 не задаёт допустимый переход:
  серверная машина состояний определяет доступные команды.
- Звёздочки на жалобах/рекомендациях и чек-лист завершения на листах не вводят новых
  обязательных полей. Источник требований и готовности завершения остаётся серверным.
- Лист07 дублирует историю под вкладкой наблюдения. В реализации история раскрывается
  отдельно, чтобы не вытеснять редактор. `Зуб16` отображать с пробелом.
- Лист05 показывает только часть схемы из-за двух макетов на одном листе. В реальном
  интерфейсе доступны все FDI, drawer не должен делать остальные зубы недоступными.
- Условные телефоны/диагнозы/зелёные отметки не копировать. Пустое состояние не означает
  «здоров»; статус отсутствует только при сохранённом медицинском состоянии.
- Таблица услуг не получается из текстового `procedures` автоматически. Старое описание
  сохраняется отдельно без выдуманных зубов, услуг, времени и статуса. Новые позиции
  `procedure_items` хранятся в существующем шифрованном версионном содержимом:
  UUID, название услуги-снимок, FDI зубов, описание, длительность. Это выполненные
  действия; планируемые остаются в `plan_steps`. Каталог используется для подсказки,
  свободное название допускается; финансовых/складских действий нет.
- Общий «Применить» для медицинского черновика не распространяется молча на существующий
  отдельный endpoint наблюдений зуба: до объединения сохранения подписать кнопку
  «Сохранить наблюдение». Это осознанное отличие от эскиза, сохраняющее текущий контракт.

### Первый реализуемый UI-срез

Восстановить страницу записи, компактную шапку и две вкладки Приём/История,
краткие медицинские поля с modal-вводом, одонтограмму с drawer, перенос и завершение
в окнах, существующий план и передачу повторной записи. Использовать существующие
сервисы/данные/ACL, не возобновлять документы/закупки и не менять регистрацию.
Структурированные позиции лечения входят в этот этап, сохраняются общей кнопкой
и удовлетворяют требованию выполненной работы при завершении. Зубы сохраняются
отдельным действующим endpoint. Новых моделей/миграций/полномочий нет.
Экспорт `procedure_items` в документы/шаблоны не принят в этом этапе: эти функции
на паузе. Не заявлять полную готовность документов или всего медицинского ТЗ.

## 11. Граница готовности

Реализованы компактная страница записи, таблица лечения и окна редактирования.
Страница клиента и новые гибкие роли не входят в текущий этап. Регистрация,
ACL и рабочая БД не меняются; серверное изменение ограничено содержимым
выполненного лечения и проверкой его наличия. Актуальные проверки и ограничения
зафиксированы в связанном checkpoint; описание макета само по себе не является PASS.
