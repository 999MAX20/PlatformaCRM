# Сценарии пользовательского прогона через «Компьютер»

**План согласован; фактические результаты48сценариев и оставшиеся варианты — в
[ведомости запуска12.11](../evidence/crm-global-run-20261112-coverage.md).**
Шаги ниже — исходные ожидания; они не подразумевают, что каждый вариант пройден.
[Среды, роли, fixtures и ограничения](README.md), [матрица](matrix.md),
[точные маршруты](inventory.md). Названия кнопок сверяются с текущей локалью;
описание действия не предполагает добавления отсутствующего control.

## Единый протокол

Каждый сценарий получает run-id, candidate, E3 URL, роль/effective permissions,
locale/viewport и исходные IDs. Вход и действия выполняются через «Компьютер».
Не использовать API/JS для обхода неработающей кнопки. Для logout/новой роли
проверять имя и Business в оболочке, не полагаться только на смену вкладки.

Для каждой строки шагов сохранять фактический результат. Общий пакет evidence E:
скриншот исходной страницы, существенного перехода/ошибки и конечного результата;
URL/время/объект без токенов; после write reload и повторное открытие объекта.
Технический readback T (отдельно от Computer) подтверждает значения, counts,
audit/event и отсутствие чужих изменений. Нет T там, где UI не может доказать
атомарность/конкурентность, значит соответствующая API-проверка остаётся открыта.

Общая очистка Q: записи остаются в synthetic run-наборе до завершения зависимых
сценариев; затем архив/cleanup по manifest или удаление всей disposable БД.
Не пытаться удалять неизменяемый payment через несуществующий UI. Переключённые
локаль/viewport вернуть в исходное состояние. Разрушительные сценарии используют
отдельные disposable fixtures и никогда не обрывают рабочие сервисы.

Во всех формах проверить invalid input, Cancel, double submit и ошибку сохранения
согласно X-UX. Эти вариации имеют отдельные results, а не подразумеваются одним PASS.
Для live письма/канала/ASR нужна выбранная E4 конфигурация; без неё L-шаг BLOCKED.

## B01. Публичный вход и новый бизнес

Связи: AUTH-01, ONBOARD-01, PUBLIC-01. Роль AN→O(C), fixture новый synthetic email.

1. Открыть `/`, переключить RU/KK/EN, перейти к входу; открыть документы и неизвестный URL.
2. На `/login` отправить пустую форму, затем неверные credentials; проверить понятную ошибку.
3. На `/signup` заполнить допустимые сведения нового C; отправить один раз, затем проверить защиту повторной отправки.
4. Завершить предусмотренный flow и открыть первую рабочую страницу; обновить её.

Ожидается: реальные страницы/локали; один аккаунт/Business/membership, автоматическая
точка; отсутствие чужих данных и ложного завершения MFA. Evidence E+T counts.
Очистка Q; создание C не даёт разрешения на регистрацию рабочего бизнеса.

## B02. MFA и устройства

Связи: AUTH-02/03/06, ACCOUNT-04. Роль O, отдельный disposable аккаунт, две сессии.

1. Войти и пройти фактически требуемый MFA; проверить неверный код до верного.
2. В `/app/account` открыть MFA/устройства, выполнить разрешённое enrollment/управление.
3. Во второй сессии подтвердить вход; из первой отозвать вторую; обновить вторую.
4. В отдельной вариации использовать recovery code и попытаться повторить его.
5. Выполнить logout и проверить возврат по старому deep link.

Ожидается: нет доступа до завершения MFA, отзыв действует в следующем запросе,
recovery одноразовый. Не фотографировать QR/секреты/коды. E redacted+T session/audit.
Очистка: восстановить доступ тестовому аккаунту, Q; не отзывать сессии владельца.

## Финальная ведомость браузерного прогона

Перед исполнением создать строки `Bxx.variant / role / locale / viewport / fixture /
expected / actual / status / evidence / defect / cleanup`. У B46 список маршрутов
является обязательным приложением: нельзя заменить его фразой «осмотрел все страницы».
Один сценарий может иметь PASS happy path и FAIL recovery; итог сценария тогда не PASS.
Сценарии зависят от fixtures, а не от случайного порядка предыдущих тестов: если B14
заблокирован, B20 получает отдельно подготовленный допустимый Appointment, с пометкой
setup, и не утверждает, что B14 прошёл.

Согласование этого файла не создаёт аккаунты, не отправляет сообщения и не запускает
«Компьютер». Исполнение начинается только по следующему разрешению пользователя.
