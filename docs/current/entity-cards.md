# Модальные карточки сущностей

Обсуждение и решение владельца от 05.11.2026, задача ENTITY-CARDS-20261105.
Владелец выбрал референс карточки клиента: центральное окно, затемнённый фон
без размытия, служебная строка, предметная шапка, боковые сведения и вкладки.
Затем разрешил документирование всего обсуждения и реализацию первой карточки — клиента.

сохранён как иллюстрация концепта; его контакты и события не являются данными продукта.

## Общая строка вкладок клиента и записи05.11

Селектор «Ещё» заменён единой строкой вкладок без переносов и видимого
ползунка. При переполнении доступны горизонтальный свайп/трекпад и небольшие
стрелки; клавиши Left/Right/Home/End переводят фокус и выбирают вкладку с прежней
защитой черновика/pending. Активная вкладка прокручивается в видимую часть строки.

## Уточнение владельца05.11: нижняя панель

В реализованных карточках клиента и записи нет нижней панели с отдельной
кнопкой «Закрыть» и разделителем. Закрытие — крестиком в правом верхнем углу
или Escape с существующей защитой черновика/pending. Область содержимого
занимает освободившуюся высоту в прежних границах окна.

## Терминология

| Термин | Значение |
| --- | --- |
| Карточка сущности | Сведения, связи, история и действия одного объекта |
| Модальная карточка | Карточка в центральном окне над затемнённой страницей |
| Drawer / выдвижная панель | Представление, открывающееся от края экрана |
| Инспектор | Область быстрого просмотра выбранного объекта, обычно рядом со списком |
| Страница сущности | Адресуемое полноценное представление объекта |

В обсуждении использовать «карточка клиента/записи/задачи», для механизма —
«модальная карточка сущности». Инспектор обозначает назначение, modal/drawer — размещение.

## Композиция по референсу

1. Верхняя строка: тип и название, «Открыть страницу», крестик.
2. У реализованных клиента/записи действия в верхней строке, имя и ключевые сведения слева; отдельной полноширинной предметной шапки нет.
3. Слева постоянные сведения, справа вкладки и основной контент.
4. Спокойная непрозрачная поверхность, разделители, зелёный акцент действующей темы.
5. Нижней строки «Закрыть» нет по последнему уточнению владельца. Редактирование имеет собственные Save/Cancel.
6. Фон только затемняется: backdrop-filter:none. Нет блюра шапки или страницы.

Исходные параметры для проверки: ширина1000–1100px, боковая колонка240–280px,
отступ24px. По утверждённому уточнению фиксированного размера клиент/запись имеют
ширину до1080px и высоту90dvh начиная с640px ширины экрана; ниже640px высота
calc(100dvh - 24px), ширина с полями12px. Высота не зависит от вкладки, загрузки
или ошибки. При1440×900 окно1080×810. Это размеры оболочки,
не разрешение заменить токены, шрифт, цвета или существующую тему.
На мобильном окно почти полноэкранное, колонки складываются. В клиенте имя и
контакты остаются открытыми; ответственный, заметки, теги и оплаты раскрываются
кнопкой «Подробнее» перед вкладками. На desktop сведения остаются открытыми.
Закрытие доступно, горизонтального overflow документа нет.
[Проверка мобильной карточки09.11](../testing/evidence/crm-ui-fixes-20261109.md).
На широком экране (от768px) шапка и вкладки закреплены, левая колонка и
содержимое правой части имеют независимую прокрутку. На телефоне/узком экране
одна прокрутка тела, строка вкладок закрепляется при достижении верха. Переход
на другую вкладку сбрасывает прокрутку её панели; черновик/pending проверяются
до переключения. Обычные Dialog и прочие drawers сохраняют прежнее поведение.

## Сопоставление с исходным кодом

CrmEntityDrawer использует правый Drawer (complex720px); Dialog и Drawer разделяют
platforma-overlay-backdrop с blur10px. CRM-шапка содержит градиентную иконку и blur.
У клиента/записи общий набор восьми вкладок. Обзор записи повторяет историю,
задачи и файлы из отдельных вкладок. Для клиента, записи и задачи есть страницы.
ClientDrawerContent использует appointments[0], но backend сортирует по-start_at:
это не гарантированная ближайшая запись. Payload ограничен limits/has_more.

Основания: frontend/src/components/crm/CrmEntityDrawer.tsx; drawers/shell.tsx,
drawers/client.tsx, drawers/appointment.tsx; components/ui/Overlay.tsx;
frontend/src/styles.css; apps/core/crm_cards.py. Это исходные наблюдения,
а не утверждение, что каждый пункт остаётся после реализации.

Специалист и сотрудник с доступом различаются: отключение входа не выключает
специалиста и не переназначает записи. Не создавать клинических данных.
Переписка остаётся рабочим Inbox. Редактор автоматизации, настройка интеграции,
длинное обращение поддержки сохраняют свои рабочие экраны; preview возможен
после отдельного анализа. Не каждой таблице нужна большая карточка.

## Карточка клиента — утверждённый первый этап

Верхняя строка: тип, «Создать запись», «Написать», дополнительные действия,
голос/открыть страницу/крестик; mobile выносит действия отдельным рядом.
Отдельной полноширинной шапки нет. Слева: имя/признаки, контакты, ответственный,
заметка, существующие теги. Обзор: ближайшая актуальная запись и краткая активность.
Все вкладки в одной горизонтальной строке: Обзор, История, Записи, Задачи,
Переписки, Заметки, Файлы, Детали. Состав ограничен прежними правами. Детали
сохраняют дополнительные поля, атрибуцию и согласия. Вкладка исторических связей
со сделками удалена из клиентской карточки по решению владельца; данные/API
сделок и другие их потребители не удаляются.
Существующие редактирование, тег, архивирование и платежи не теряются.

«Написать» ведёт к доступной переписке либо разрешённому каналу; не отправляет
сообщения автоматически. Маскированный номер референса не вводит новое правило
PII: отображение зависит от серверной проекции и прав. Нет вымышленных менеджеров.
Ближайшая запись выбирается из актуальных незавершённых неархивных записей
с разрешённым VIEW; прошедшие/отменённые/неявки/завершённые не подменяют её.
Текущий сеанс может быть показан, пока end_at ещё не прошёл. При отсутствии
данных честное empty state; при ошибке retry, при запрете не изображать нулевой итог.

## Карточка записи — реализация следующего этапа05.11.2026

Вопрос: кто, когда, на какую услугу и к кому записан, каково состояние и следующий шаг?

| Зона | Состав |
| --- | --- |
| Служебная строка | Запись №, основные действия и меню, голос, открыть страницу, закрыть; на телефоне действия отдельным рядом |
| Компоновка | Отдельной полноширинной предметной шапки нет; вкладки начинаются сверху правой колонки |
| Сведения слева | Имя клиента как переход в карточку, дата и интервал отдельными строками, доступные контакты, услуга, специалист/ресурс, филиал, ответственный, источник, статус |
| Обзор | Ключевые данные, заметка, компактный план/этап, последние события |
| История | Создание, подтверждение, переносы, отмена, завершение; время/автор |
| Задачи | Только задачи этой записи, доступное создание |
| Файлы | Вложения записи и разрешённые операции |
| Переписка | Только связанный источник и только при доступе |

Другие посещения клиента открываются через клиента; вкладка «Записи» внутри
одной записи не нужна. Ответственный ведёт запись, специалист оказывает услугу,
ресурс может быть помещением/оборудованием: не сводить их в одно поле.
Незавершённая запись допускает существующие подтверждение/перенос/завершение/
отмену/неявку по серверным правилам. Отмена/неявка и досрочное завершение требуют
действующей причины. Terminal-состояния не открываются заново через новый UI.
Повторная запись и архив/restore только по существующим правам.
Одна главная кнопка; разрушительные/редкие действия не конкурируют с ней.
Стоимость записи не вычислять из текущей цены услуги: нужен достоверный snapshot
и установленная связь платежей. Менять денежную модель этим дизайном не разрешено.

## Общая техническая модель и поведение

- Общая оболочка `Dialog` с `presentation="entity"`; отдельные ClientCardModal и
  AppointmentCardModal, действия и обзор записи вынесены в feature-компоненты.
- Modal и полноценная страница разделяют API/данные/действия; сервер сохраняет права.
- Закрытие возвращает фильтры, страницу, прокрутку и фокус исходного списка.
- Клиент↔запись переключаются в одной видимой карточке с кнопкой возврата.
  Из клиента доступны ближайшая запись и список записей; из записи — клиент.
  Несохранённый ввод защищён перед переходом. Закрытие возвращает исходный список
  и фокус. В календаре инспектор скрыт на время карточки и возвращается при закрытии.
- «Открыть страницу» только с реальным маршрутом. Deep link и reload должны иметь
  определённое представление; новые маршруты не изобретать без необходимости.
- Draft/pending защищаются при закрытии, Escape и навигации. Nested menus закрываются
  раньше карточки. Не терять введённый текст при фоновой загрузке.
- Focus trap/return, scroll lock, недоступность фона для взаимодействия, именованные
  controls, keyboard tabs, reduced motion; проверить в браузере, не объявлять по JSX.
- Loading, empty, forbidden, missing, error/retry, stale conflict — разные состояния.
- Query scope включает Business/actor/object. Ошибка прав не оставляет видимый старый payload.
- Ограниченные related lists не называются полными: counts/has_more и путь к остатку.
- RU/KK/EN, timezone бизнеса, длинные имена/телефоны, пустые связи и мобильный экран.

### Граница реализации записи05.11

Открывается из таблицы Записей, связанных карточек клиента и «Открыть карточку»
инспектора Календаря. Основные вкладки: Обзор, История, Задачи; дополнительные:
Файлы, Заметки, Дополнительные поля, Переписка. Дублирующей вкладки Записи нет.
Обзор содержит комментарий, существующий план и три последних события; полная
доступная история находится отдельно. Ограничение выборки заметок обозначается.

Подтверждение, завершение, отмена, неявка и перенос используют прежние API и
серверный expected_updated_at. Причины/перенос защищены от закрытия при отправке;
черновик требует явного отказа. Конфликт версии сохраняет причину и допускает
повтор после явного обновления. Terminal-запись предлагает существующее создание
повторной записи с предзаполнением. Архивирование/восстановление этим этапом не
перенесены из существующих рабочих экранов в карточку; денежные действия не добавлены.

Кэш разделён по Business/actor/объекту; 403/404 скрывают сохранённые сведения,
временный сбой сохраняет черновик. Контекстный голосовой вход клиента/записи сохранён.
Новые модели, endpoint, права, деньги, уведомления и BusinessEvent не вводились.
