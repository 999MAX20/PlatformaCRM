Вывод: общая система подключена, но корректность всех потребителей не обеспечена.

## Подтверждённые находки

### A01 · P1 · Ошибка создания клиента скрыта за формой; повтор выполняет другую операцию

`frontend/src/features/clients/ClientsPage.tsx:281,309`: saveClientMutation.error
включён в pageError; ErrorState размещён за диалогом. Создать клиента → POST503:
в форме0 ошибок, на фоновой странице1, toast0; ввод сохранён. После закрытия формы
«Повторить» делает refetch списков, POST остаётся1, ошибка остаётся.
[Снимок](alert-audit-20261103-assets/client-modal-error.png).
Последствие: пользователь не получает доступной причины отказа и восстановления.
Минимум: ошибку mutation держать в форме; повторять её через submit с сохранённым
вводом и существующими правилами идемпотентности. Ошибки чтения оставить странице.
Проверка исправления:503→видимая ошибка→повтор→успех, keyboard и сохранение полей.

### A02 · P2 · Одна ошибка ресурса показана дважды

`frontend/src/features/resources/ResourcesPage.tsx:172–177,392`,
`frontend/src/features/resources/components/ResourceEditModal.tsx:102`.
PATCH503 выводит одинаковое сообщение в форме и toast; на390px toast занимает
дополнительную область над формой. ErrorState получает строку, supportDetails=0.
[Снимок](alert-audit-20261103-assets/resource-duplicate-error.png).
Минимум: одна постоянная ошибка внутри активной формы, исходный AppError для
recovery/details; toast оставить для операций без открытой формы.
Проверка: один канал объявления ошибки, retry и мобильная кнопка сохранения доступны.

### A03 · P2 · Несовпадение паролей теряет конкретную причину

`frontend/src/features/account/AccountPage.tsx:80,173`: локальный new Error с
переведённой passwordMismatch проходит общую нормализацию и становится общей ошибкой.
В браузере запросов смены пароля0, но вместо «Пароли не совпадают» показано
«Не удалось подтвердить результат… обратитесь в поддержку».
[Снимок](alert-audit-20261103-assets/password-mismatch.png).
Минимум: локальная валидация у поля подтверждения с aria-связью и переводами;
не ослаблять общую очистку серверных ошибок ради этого случая.
Проверка: mismatch без API, точная причина, исправление поля и успешный submit.

### A04 · P3 · Подтверждение сохранения профиля остаётся при новом изменении

`frontend/src/features/account/AccountPage.tsx:72–74,108`.
После успешного сохранения новое редактирование оставляет «Профиль обновлён»
до таймера2600ms; submit уже активен, draft отличается от сохранённого.
[Снимок](alert-audit-20261103-assets/profile-stale-success.png).
Минимум: подтверждение конкретной операции общим toast либо сброс inline success
при изменении формы. Проверка: save→edit не утверждает сохранённость нового draft.

### A05 · P2 · Недоступные счётчики колокольчика представлены нулями

`frontend/src/components/layout/NotificationBell.tsx:80–85,100–104`:
due/urgent используют `data?.… || 0` независимо от ошибки загрузки.
При503 summary/feed видны «0 требуют внимания сейчас · 0 срочных» и ошибки.
[Снимок](alert-audit-20261103-assets/bell-failure.png).
Минимум: pending/unknown/error отдельно от достоверного0; при stale data обозначить
устаревание и дать повтор. Не выдавать сбой за отсутствие работы.
«Всё прочитано» в снимке — существующая подпись кнопки markAllRead, а не отдельное
утверждение об успешной загрузке; само по себе это не доказательство дефекта.
Проверка:503 без кеша и со stale кешем, retry, настоящий0 и ненулевой результат.

### A06 · Расхождение ожидания размещения · ServiceStatusNotice остаётся над страницей

`frontend/src/components/layout/AppLayout.tsx:127` и
`frontend/src/components/notifications/ServiceStatusNotice.tsx:26`.
Браузер показывает «Нет свежих данных о фоновой обработке» в основном контенте.
Текущий frontend-контракт прямо сохраняет этот блок inline; это не регрессия
компонента. Но ожидание «никаких системных уведомлений сверху со сдвигом» не выполнено.
Если это целевое правило, переместить глобальное состояние сервиса в постоянную
карточку host справа снизу с обновлением/закрытием и корректной повторной активацией.
Ошибка конкретной формы/страницы должна оставаться возле своего действия.
Проверка: unknown/degraded/recovered не сдвигают страницу, действия доступны в modal
и390px; одинаковый эпизод не порождает новые карточки.

## Порядок исправлений и корректные решения

Сначала A01/A03 (причина и восстановление), затем A02/A05, затем A04 и согласование
целевого размещения A06. Одно событие — один основной канал сообщения; системное
состояние не должно исчезать по короткому таймеру без другого доступного индикатора.
Ошибки полей оставить у полей, ошибки загрузки — в недоступном блоке с повтором,
ошибки submit — в форме, результаты команд без формы — в toast, долговременную
историю — в центре уведомлений. Не переносить всё подряд в toast.

Общие компоненты уже поддерживают четыре тона, stable host внутри активного modal,
паузы таймера на hover/focus/action, reduced motion, dedupe и восстановление фокуса.
Эти решения полезны; нужен ремонт потребителей и правил выбора канала.
Backend/permissions/BusinessEvent/AI/migrations/API changes: none.
Roadmap и продуктовые контракты не изменялись: аудит не закрывает приёмку и не меняет
требования. Новый документ — evidence, не параллельный roadmap.
