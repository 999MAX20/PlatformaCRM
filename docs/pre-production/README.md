# Технические паспорта пилота / pre-production

Этот раздел описывает фактическое состояние основных функций PlatformaCRM перед
продакшном: что умеет модуль, на каких данных работает, какие действия разрешены,
чем защищён и в какой среде проверен. Первый зафиксированный срез — 07.10.2026.

Начать с [состояния проекта](project-state.md), затем открыть паспорт модуля.
Это отдельный каталог состояния продукта, а не новая очередь разработки.
[Открытая приёмка](../current/acceptance.md) сохраняет недоказанные границы, [V1](../current/product.md) и предметные контракты — требования,
[отчёты проверок](../testing/task-state/PRIMARY-SESSION.md) — доказательства.
Паспорт ссылается на них и не меняет правила или статус приёмки самостоятельно.

[Общая карта реализации](capabilities.md) сверяет модули с исходниками и отделяет
наличие кода от недостающей приёмки.

## Как вести документацию

Для нового паспорта использовать [шаблон](module-template.md). Один модуль — один
актуальный документ; значимые изменения кратко добавлять в его журнал, а подробные
команды/ошибки/артефакты оставлять в исходном отчёте проверки и Git.

При изменении функции в рамках согласованной задачи обновлять её паспорт:
поведение, версию исходников, ограничения, применимые доказательства и журнал.
При новой проверке или решении о паузе/допуске обновлять соответствующие поля.
Чисто документальный commit не меняет версию программного поведения.

Версия паспорта — дата среза и Git SHA реализации. Это не номер релиза, тег или
обещание deployment. После изменения кода прежний PASS переносится только на
неизменившиеся проверенные границы; старый live-тест не сертифицирует новый prompt.

Всегда различать: **реализовано → проверено в указанной среде → опубликовано в Git
→ развёрнуто → допущено к работе с реальными клиентами**. Пауза разработки отдельно
от отключения runtime. Если подтверждения нет, писать «не подтверждено» со ссылкой
на недостающую приёмку. Не хранить здесь секреты, персональные данные или полные логи.
