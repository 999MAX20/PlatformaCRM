## Как работает поиск

Это dropdown в общем header, а не отдельная поисковая страница или AI-поиск.
На desktop открывается фокусом/вводом; на mobile — кнопкой лупы. Пустая строка
показывает доступные элементы. Запрос обрезается по краям; серверные hooks ждут
300 мс. Поиск не меняет данные, только открывает существующие сущности.
Escape и нажатие вне области закрывают dropdown; крестик очищает непустой запрос,
а на mobile при пустой строке закрывает поле. После выбора результат закрывается.
`Ctrl/Cmd+K` относится к отдельной command palette, не к этому dropdown.

| Сущность | Фактические поля | Полнота / порядок | Открываемый маршрут |
| --- | --- | --- | --- |
| Клиент | Имя, телефон, email; дополнительно нормализованные телефон/email | Серверный поиск, по 20, «Показать ещё», новые сначала | `/app/clients?client=id`, затем карточка `/app/clients/id` |
| Запись | Имя, телефон, email доступного клиента | Серверный workspace, по 20, «Записи · Показать ещё», `start_at` по убыванию | `/app/appointments/id` |
| Задача | Название, описание, технические status/priority; имя клиента только если он попал в текущую клиентскую выдачу | Локальный substring только по первой API-странице (50); затем общий лимит с диалогами | `/app/tasks?task=id` |
| Диалог | Фактически external_user_id, channel, status. Код также ожидает client_name/client_phone/last_message, но legacy API не возвращает эти поля | Локальный substring по первой API-странице (50), последние обновлённые сначала; общий лимит с задачами | `/app/conversations?conversation=id` |

Сначала выводятся все загруженные клиенты, затем записи, затем диалоги и задачи.
Последние две категории вместе ограничены 12 совпадениями, а при пустом запросе
8 элементами. Нет ранжирования по точности/релевантности, исправления опечаток,
транслитерации, семантики, поиска по истории сообщений, общего счётчика найденного
или отдельной полной страницы результатов. Нет фильтра по типу сущности.
Сервисы подгружаются как справочник подписи записи, а не самостоятельные результаты.
Сотрудники, ресурсы, платежи, история, настройки и интеграции не индексируются.
Lead/Deal намеренно скрыты текущим pilot-контрактом; их отсутствие не новая ошибка.
«Вся CRM» означает отсутствие ограничения текущей страницей, а не поиск каждого поля
каждого модуля. Новый scope не является межтенантным доступом.

### Права и изоляция

Клиентский и record hooks проверяют view/capability, явно передают текущий Business,
включают business/user/query в cache key. Backend повторно ограничивает queryset по
membership, resource и object scope; скрытые данные клиента исключаются из поиска
связанных записей (`client_search_q` + `client_relation_q`). Архив обычно исключён.
40 тестов clients/search + scheduling/workspace прошли, включая запреты, чужой
Business, отдельный Client view, пагинацию и невалидные параметры.

Для задач/диалогов generic hooks не передают текущий Business: backend возвращает
доступные пользователю бизнесы. Поэтому при нескольких memberships возможна смесь
доступных бизнесов, в отличие от клиентов/записей. Это несогласованная область,
а не доказанная выдача недоступного tenant. Общий QueryClient пересоздаётся по
identity/access scope в `app/providers.tsx`; отсутствие user в generic query key
само по себе не доказывает утечку между сессиями. Multi-business browser сценарий
в этом срезе отдельно не сертифицирован.

### Подтверждённые ограничения и приоритет

1. **Высокий, полнота задач/диалогов.** `createCrudApi.list()` берёт только одну
   страницу и теряет `next`; запрос не отправляется серверу. Элемент вне первых
   50 не может попасть в результат. Даже среди загруженных совпадений диалоги могут
   занять все 12 мест и вытеснить задачи. Это следует из действующего кода/API;
   нагрузочный прогон большой базы не выполнялся.
2. **Высокий, контракт диалогов.** Реальный ответ `/api/bot-conversations/` в
   тестовой БД не содержит ожидаемых client_name/client_phone/last_message.
   Пользователь ищет знакомого клиента или текст сообщения и не получает диалог.
   Inbox использует ту же BotConversation-модель, поэтому разные API не означают
   разные ID. Исправление требует согласовать поисковый consumer с Inbox API.
3. **Средний, ложная уверенность в пустой выдаче.** Loading/error/retry есть только
   для клиентов/записей. Ошибки tasks/botConversations/services игнорируются.
   «Ничего не найдено в данных CRM» может означать неполную загрузку, а не отсутствие.
4. **Средний, ожидания полей.** Услуга/заметка записи и заметки/источник клиента
   показаны/упомянуты в локальном haystack, но не участвуют в серверном поиске.
   Поиск записи по «Консультация» не находит существующие записи этой услуги.
   В tasks уже есть `client_name` API, но компонент ищет имя через отдельную
   клиентскую выдачу: связь пропадает, если клиент за пределами её загруженных страниц.
5. **Средний, единый Business.** Задачи/диалоги и клиенты/записи имеют разные правила
   выбора Business при нескольких memberships; нужен явный одинаковый scope.
6. **Ниже, UX/локализация.** Status/priority задач и channel/status диалогов видны
   как `open`, `high`, `website`; fallback `Conversation #...` не локализован.
   Крестик назван «Закрыть поиск», хотя с текстом он очищает его. Возможны два
   крестика из-за нативного `type=search` и собственного X. Нет навигации стрелками
   и выбора первого результата Enter; доступны обычные Tab/Enter на ссылках.
   Escape снимает фокус с input, но не восстанавливает его на mobile-триггер.

### Практическая полезность и дальнейшая работа

Полезен для быстрого поиска клиента по имени/контакту, открытия его записи и
поиска задачи в небольшом списке. Нельзя считать надёжным универсальным поиском
по большой CRM: отрицательный результат по задачам/диалогам сейчас не доказателен.

Рекомендуемый следующий этап: серверные paged searches задач и Inbox в текущем
Business, корректные поля ответа, независимые лимиты/«ещё» по категориям, явные
состояния каждой категории, затем keyboard/локализация. Сначала исправить полноту
и контракт, а не добавлять AI или новый поисковый движок. Это рекомендации аудита;
изменение селектора не выдаётся за их реализацию.

### Попытки и границы

Первая сборка остановилась на чужом незавершённом `PaymentsPage.tsx:114` (TS1005).
После изменения этого файла его владельцем повторная сборка PASS. Первоначальный
bundle-check общего `dist` обнаружил два app-shell chunks из параллельных сборок;
чистый отдельный output этой задачи устранил конфликт. Чужие файлы не исправлялись.
Browser harness скорректирован после диагностик: выбирать видимый input из двух
responsive Header instances, ждать отрисовку/учитывать canonical client redirect,
не ждать новый HTTP для уже кэшированного запроса, кликать вне fixed header.
Ошибки harness не скрыты как продуктовые PASS; финальные scripts прошли полностью.

Backend/migrations/API не менялись: migration drift и все backend-сюиты не запускались.
Права/tenant покрыты указанными backend тестами; все роли в браузере не сертифицированы.
Полный release gate, live deployment и CI этой задачи не запускались. Нового этапа
roadmap нет; product/CRM/access/AI/integration contracts и README не требуют изменений,
поскольку APIs, права, setup и эти домены не изменены. Frontend contract, capabilities,
STATUS, PRIMARY и реестр evidence обновлены; исторические отчёты не переписаны.
