## Резервный аудит чтения — К07, локальная реализация

Миграции medical0034/0035 добавляют медицинские файлы, версии, аудит и FDI-связи.
Они проверяются в изолированной БД; к рабочей БД в рамках К07 не применялись.
Файловый сценарий требует этих миграций и работающего существующего scanner worker.
Допускаются PDF/JPG/JPEG/PNG/WEBP до10MiB, с проверкой сигнатуры/MIME; это текущий
технический контракт, не приёмка всех реальных клинических форматов L12.
Загрузка и проверка bytes ограничены памятью; имена и описания зашифрованы отдельно,
storage path непрозрачен. Фактическое шифрование хранилища, backup и retention требуют
проверки целевой среды. Общая файловая квота учитывается; PG evidence конкурентности
покрывает медицинские загрузки между собой, не гонку с обычным CRM uploader.

`MEDICAL_READ_AUDIT_RESERVE` пуст по умолчанию. При отказе основного medical audit
чтение остаётся закрытым, пока резерв не настроен и не подтвердил запись.
JSON-конфигурация: `bucket`, `endpoint` (только `https://storage.yandexcloud.kz`),
`region`, `access_key`, `secret_key`, `kms_key_id`, `retention_days` (целое 1–36500).
Это технический диапазон, не утверждённый срок хранения. Срок требует решения L08;
ключи/конфигурацию передают через секреты среды, не через UI или репозиторий.
Нужен отдельный private versioned bucket с Object Lock, отдельный service account,
KMS и подтверждённое размещение в Казахстане. Общий bucket/его access key отвергаются.
Приложению нужны PutObject, GetObjectRetention и HeadObject для проверки своей записи;
публичный доступ и право обхода/снятия защиты не нужны. Provisioning приложение не делает.

Каждый разрешённый fallback-read синхронно записывает отдельную версию с COMPLIANCE
до заданной даты и SSE-KMS. Успех требует VersionId, подтверждённых retention/KMS,
размера и SHA256 metadata. Конверт содержит только Business/Patient ID для восстановления
контекста AES-GCM; actor, точные ссылки/ревизии и время внутри encrypted_event.
Клинические тексты, имена файлов, токены и provider errors в журнал не включаются.
Событие `authorized` фиксирует разрешение чтения, не обещает доставку браузеру.
При неопределённом результате запись может остаться в резерве, но данные не выдаются.
Автоматического удаления, ослабления блокировки или фонового «дописать потом» нет.

Для проверки полученной из защищённого хранилища конкретной версии объекта оператор
использует `python manage.py inspect_medical_read_audit <локальный-файл> --event-id <UUID-из-имени-объекта>`.
Команда требует доступ к ключам `MEDICAL_DATA_KEYS`, проверяет AES-GCM, tenant context,
event UUID, схему/типы/время и печатает только проверенное audit-событие. Лимит входа16KiB.
При ошибке не печатает частичных данных. Запросов к БД/облаку, импорта/удаления или
изменения primary audit нет. Старый ключ сохраняют в keyring для чтения старых событий
при ротации активного ключа. Результат проверки сам содержит защищённые идентификаторы:
хранить его в разрешённом операторском контуре, не в общем логе приложения.
UUID сверяют с точной версией S3, сохранённой при получении объекта; отдельный доверенный
манифест версий/периода нужен для доказательства полноты журнала. Успешная проверка одного
файла доказывает его подлинность, но не отсутствие пропусков и не фактическую облачную
неизменяемость. Это остаётся частью эксплуатационной приёмки L13.

Локальные тесты проверяют контракт через подменённый S3 client и настоящий botocore
Stubber без сети; offline recovery/ротация/отказы локально проверены. Облачная надёжность,
IAM, закрытость bucket, восстановление/сверка журнала и фактический retention ещё не
приняты (L07/L08/L13). Не включать это как эксплуатационно проверенный резерв.
Изолированный verification runner принудительно отключает эту настройку; тесты
включают синтетическую конфигурацию только вместе с подменой provider client.
Основание адаптера: [Yandex KZ Object Lock](https://yandex.cloud/ru-kz/docs/storage/concepts/object-lock).

Медицинская migration0014 (DENTAL-MCS срез59) добавляет encrypted closure reason,
PROTECT responsible member и audit action/constraints для завершения участия.
Проверена в disposable DB вместе с445 medical tests/check/drift; к рабочей БД
не применялась. Новых env/provider настроек нет. Командный HTTP и интерфейс
приглашения/принятия/завершения участия подключены и локально проверены на desktop/mobile.
Это не подтверждение production, обычного завершения или временного доступа на24 часа.

## Словарь поверхностей одонтограммы — DENTAL-MCS, локальная реализация

`MEDICAL_TOOTH_SURFACE_POLICIES` — JSON-объект с ключами строковых Business ID.
Значение каждого бизнеса: `reference`, `approval_reference` (непустые строки до200
символов) и `teeth` — объект номер зуба → список технических кодов поверхностей.
Необязательный `labels` задаёт каждому использованному коду объект из трёх непустых
подписей `ru`, `kk`, `en` до200 символов. Если labels присутствует, он покрывает ровно
все коды из teeth; частичные переводы/лишние коды отвергаются. Политики без labels
сохраняют совместимость (API возвращает пустой объект подписей для кода). Утверждённые
подписи предоставляет та же медицинская проверка; смена смысла/подписей требует новой
reference и сохранения предыдущей утверждённой версии словаря вне этой настройки.
Коды: строчная латинская буква, затем буквы/цифры/подчёркивания, всего до32 символов.
Допустимые поверхности каждого зуба и реквизиты утверждения предоставляет медицинская
проверка; приложение не содержит встроенной утверждённой легенды. Конфигурация пуста
по умолчанию: запись отдельной поверхности без неё блокируется. Свободное наблюдение
по зубу целиком не выбирает словарь. Смена reference требует перечитать актуальную
версию перед записью; ссылка и approval_reference сохраняются внутри encrypted payload.
Заполнение настройки само по себе не доказывает медицинское утверждение. Реальные
значения в этой задаче не устанавливались. GET surface-options возвращает только
текущую reference и коды/подписи выбранного зуба после проверки основания доступа
к пациенту; approval_reference в этот ответ не включается. Отсутствующая настройка
бизнеса даёт configured=false, повреждённая —503. Это API чтения, не редактор настройки;
публичная административная UI настройки не реализована. Срез56:41 focused/dependent tests

одонтограмме, локальные browser evidence указаны в основном checkpoint.

## Медицинские ключи: локальная реализация DENTAL-MCS

Медицинский слой использует отдельные параметры окружения:
`MEDICAL_DATA_KEYS` — JSON-словарь key ID → base64 ключа AES-256 (32 байта),
`MEDICAL_DATA_ACTIVE_KEY_ID` — ключ для новых записей,
`MEDICAL_IDENTITY_INDEX_KEY` — отдельный 32-байтовый base64 ключ HMAC поиска ИИН.
Значения не публикуются в документации, логах или API. Ключи коннекторов и Django
SECRET_KEY не являются fallback. По умолчанию значения пусты: обычная CRM работает,
а медицинская криптографическая операция без конфигурации возвращает безопасный503.
Рабочие ключи/инфраструктура в рамках этого среза не настраивались.
Для создания пациента этот HMAC-ключ также используется в отдельном пространстве
назначения medical command: payload и пользовательский idempotency key превращаются
в keyed fingerprints до передачи общему CRMCommandIdempotency. Открытые ИИН/адрес/
дата рождения не сохраняются в таблице команд; response cache содержит только
ссылку на ресурс без медицинского содержимого. Проверка replay всё равно требует
актуальных прав. Смена HMAC-ключа влияет и на поиск, и на fingerprint повторов,
поэтому не является обычной сменой encryption key.

Шифрование аутентифицирует Business, Client/subject, назначение поля и key ID.
Для смены encryption key старый ключ сохраняется в keyring до проверенного
перешифрования и решения о восстановлении из резервных копий. Удаление старого
ключа делает его данные недоступными. HMAC индекс зависит от отдельного стабильного
ключа и Business; его нельзя просто заменить в окружении — нужен отдельный
проверенный процесс перестроения индекса с защитой уникальности. Такой процесс,
хранение/выдача ключей, backup/restore и реальные внешние подтверждения ещё открыты.
Синтаксические12 цифр ИИН не подтверждают личность. Профиль/криптографические
примитивы не означают готовность медицинских API или допуска к запуску.
Для первоначального подтверждения личности добавлен отдельный server setting
`MEDICAL_IDENTITY_VERIFICATION_POLICIES`: JSON object с ключами строковых Business ID.
Каждое значение содержит `reference` (версия протокола), `approval_reference`
(ссылка на реально полученное внешнее утверждение), `trained_member_ids` (BusinessMember
IDs обученного ресепшна), `methods` (код способа → `required_fields`/`optional_fields`,
списки кодов полей фиксации). Коды — `[a-z][a-z0-9_]{0,63}`; значения полей — строки
до2000 символов, зашифрованные вместе с evidence. Встроенного списка допустимых
документов/возрастов нет. Реальные протокол/состав фиксации/обучение нужно подтвердить
до настройки; техническая запись approval_reference не является доказательством
экспертизы. Сейчас setting пуст: verify503, обычная CRM и предварительные профили
остаются доступны. Настройка протокола через пользовательский UI ещё не реализована.
Для формы проверки каждый метод дополнительно содержит `label` (объект с непустыми
ru/kk/en строками до300 символов) и `field_labels` (код каждого required/optional
поля → такой же объект). Эти два атрибута задаются вместе; лишние/пропущенные поля
и языки отклоняются. Старый протокол без обоих атрибутов допустим для доменной
команды, но endpoint формы возвращает503, пока полного описания нет. Подписи —
текст для отображения, не HTML и не встроенная правовая классификация.
GET `/api/medical/patients/verification-form/` требует текущие reception/approve,
филиал и обучение; возвращает только reference и методы с labels/required/max_length.
Approval reference и список обученных сотрудников в ответ не попадают. Конфигурация
остаётся серверной, её содержимое и переводы должны соответствовать утверждённому
протоколу; наличие JSON не подтверждает внешнее согласование.
Для подтверждения представительства отдельный setting `MEDICAL_REPRESENTATIVE_POLICIES`:
те же Business keys/reference/approval_reference/trained_member_ids/methods и
дополнительно `permissions` (непустой список уникальных кодов, максимум30) и
`requires_expiry` (строгий boolean). Разрешения выбираются явно только из этого
протокола; отсутствие конечной даты допустимо лишь при requires_expiry=false.
Для формы и методов используются label/field_labels как выше; `permission_labels`
дополнительно отображает каждый разрешённый код на полный ru/kk/en label. При наличии
этого поля его состав проверяется и для commands; форма без него закрыта503.
GET `/api/medical/patients/representative-form/` отдаёт только безопасный whitelist
настроек обученному reception/approve, без служебных ссылок и списка сотрудников.
Политика пациента не служит fallback для представителя. По умолчанию setting пуст,
поэтому подтверждение закрыто503. Отзыв уже существующей связи не зависит от
содержимого этого setting, чтобы удаление протокола не мешало закрыть полномочия.
Период нормализуется в UTC; основания/полномочия/снимок шифруются отдельно для
конкретной связи. Получение PK и окончательное шифрование происходят в одной
транзакции, до аудита/commit. Administrative API list/verify/revoke уже подключён.
Пользовательская форма подключена и проходит browser acceptance; выдача документов
ещё не подключена. Синтетические тестовые протоколы не являются нормативным утверждением.
[Проверки и остаток](../testing/task-state/DENTAL-MCS-20261122.md).

## Лимиты XLSX импорта

`MAX_UPLOAD_SIZE_MB` ограничивает исходный файл (по умолчанию10МБ); AV проверяет
те же байты перед разбором. XLSX дополнительно проверяется до `load_workbook`:

| Настройка | По умолчанию | Ограничение |
| --- | --- | --- |
| `IMPORT_MAX_ROWS` | 5000 | Строки данных плюс одна строка заголовка на лист; учитываются физические пустые строки и координаты |
| `IMPORT_MAX_COLUMNS` | 256 | Столбцы, координаты ячеек и заявленный диапазон XLSX |
| `IMPORT_XLSX_MAX_ENTRIES` | 256 | Число записей ZIP |
| `IMPORT_XLSX_MAX_EXPANDED_MB` | 20 | Суммарный разжатый размер всех записей ZIP |
| `IMPORT_XLSX_MAX_COMPRESSION_RATIO` | 200 | Максимальное отношение разжатого размера записи к сжатому |

Проверяются все XML-части/листы книги, хотя импортируется активный лист. DTD,
дублирующиеся ZIP-записи и шифрование отклоняются. Завышенные dimensions дают400;
заниженные не обрезают реальные строки. Превышение лимита не обрезает файл молча:
нужно уменьшить файл, удалить лишние листы/пустые диапазоны или разделить импорт.
Настройки — технические ограничения ресурсов, не коммерческие квоты.
Preview/confirm повторяют проверки; рабочие env/БД этой задачей не изменялись.
Версия и scoped evidence — AUD-22-20261021 в
[checkpoint](../testing/task-state/PRIMARY-SESSION.md#aud-22-20261021--bounded-xlsx-parsing).

## Карантин и антивирус

[core](../../apps/core) хранит приватные файлы и scan state; pending/scanning/
clean/infected/error. ClamAV INSTREAM разрешает файл только по корректному OK,
не по timeout/неизвестному ответу; fail closed. Worker leases/checksum защищают
от старого результата после замены/повтора. До clean запрещены download/использование
и parsing импортов; raw storage URLs/ручного обхода quarantine не добавлять.

## STAND-ACCESS-20261029 — пароль доступа к сетевому стенду

Для закрытого стенда обязателен `compose.stand.yaml` поверх базового Compose.
Обычная локальная конфигурация не включает эту защиту. Это дополнительный вход
перед приложением, не замена аккаунтов, MFA или tenant permissions.

`deploy/stand-access` — автономный Node24 сервис без npm-зависимостей. Caddy
проверяет каждую страницу, API и статический файл через forward_auth до upstream.
Форма `/_stand/access` содержит только пароль, RU/KK/EN, показ/скрытие, состояния
проверки и ошибки. Использует снимок semantic tokens проекта в brand.json;
изменения исходных tokens нужно синхронизировать в этот адаптер.

Пароль хранится как scrypt salt/hash. Cookie HttpOnly/Secure/SameSite=Lax,
без Domain, действует8 часов. Смена hash или signing key с пересозданием gate
отзывает все старые сеансы. `/_stand/access` после входа позволяет закрыть доступ
на текущем устройстве (очистка cookie); это не отзыв украденной копии токена.
CSRF проверяется подписью cookie/token и точным Origin. Referrer-Policy должна
оставаться strict-origin-when-cross-origin: no-referrer делает Origin:null при
отправке формы Chromium. Нет session/query secrets, пароля в HTML или логах.

Не более10 проверок пароля/IP и120 суммарно за15 минут. Счётчики сохраняются
в named volume `/state`; gate не масштабируется несколькими экземплярами с этим
локальным файлом. Перезапуск не сбрасывает лимит; удаление volume сбросит его.
Ключ IP берётся из перезаписанного Caddy X-Stand-Client, а не входного XFF.
За внешним CDN/reverse proxy потребуется отдельная проверка trusted-proxy/IP
настройки; текущий контракт — прямой публичный Caddy на VM.

На каждом сервере оператор запускает из корня проекта:

```text
node deploy/stand-access/setup.mjs https://REAL_STAND_DOMAIN
```

Интерактивный ввод скрыт; пароль минимум16 символов, отдельный для каждого
проекта. Скрипт создаёт игнорируемый `.env.stand.local` (не перезаписывает),
содержит STAND_ORIGIN, WEB_DOMAIN, STAND_PASSWORD_HASH, STAND_SIGNING_KEY,
STAND_WEBHOOK_PATHS. Это секретный server-only файл: не коммитить/публиковать.
STAND_ORIGIN должен совпадать с HTTPS origin публичного домена. Локальные тестовые пароли заданы в игнорируемых ENV; публичный сервер ещё не настроен. Для ротации новый файл генерируется оператором в закрытом
каталоге, затем безопасно заменяет серверную конфигурацию и пересоздаётся gate.

По умолчанию webhook-исключений нет. STAND_WEBHOOK_PATHS — JSON-массив точных
API paths; исключается только POST, не GET/OPTIONS или подмаршруты. Добавлять
только реально используемые входящие endpoints с собственной проверкой подписи,
секрета и повтора в backend. Не разрешать целиком /api/, login, files, health.
Gate не подтверждает подлинность webhook: это обязанность действующего адаптера.
Нативные тестовые приложения должны пройти тот же form/CSRF flow с cookie jar
и Origin; их токен обычного входа не заменяет допуск к стенду. Cross-site OAuth
POST callbacks и внешние виджеты требуют отдельной проверки перед активацией.

Публичны только80/443; остальные контейнеры/БД/gate не имеют published ports.
Проверить firewall и отсутствие альтернативных origin/IP перед приёмкой сервера.
Объектное хранилище остаётся приватным: gate не может закрыть публичный S3 URL
или отозвать уже выданный presigned URL. Резервные копии/бакеты отдельно защищены.
Отказ gate даёт502/503 и не открывает приложение. No-store/noindex не заменяют
контроль доступа и не удаляют ранее скачанные файлы/кэш на устройствах.

Проверки (без рабочей БД и реальных провайдеров):

```text

node deploy/stand-access/verify-compose.mjs

```

Для verify-edge задать CADDY_BIN (Caddy2.10.2); для standalone Compose можно
задать COMPOSE_BIN, иначе используется docker compose. CI stand-access.yml
повторяет HTTP/Compose/реальный Caddy boundary. Docker image build и реальная

на конкретное развёртывание; команды здесь не выполнялись):

