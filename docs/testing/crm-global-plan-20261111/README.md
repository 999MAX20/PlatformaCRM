## Что именно входит

Три отдельных результата после согласования:

- Функциональная корректность реализованных domain/API/worker операций, включая
  текущие права, Business/branch scope, жизненные циклы, деньги и сохранность данных.
- Проходимость пользовательских сценариев через настоящий UI с помощью
  «Компьютера»: навигация, ввод, ошибки, возврат к работе, сохранение после reload.
- Отчёт о пределах: что проверено на одной версии, что заблокировано окружением,
  какие обязательства требуют реальных внешних систем или решения владельца.

Основной merchant-процесс: Клиент → Запись/план → работа → история/оплаты/аналитика.
Lead/Deal сохраняются в API и legacy-входах; их проверка отдельна от нового процесса.
Планы посещений организационные: создание этапов, назначение времени, изменение,
история и права. Не подразумевать реализованный расчёт пакетного долга/распределения
оплаты только из наличия VisitPlan. Payment receipts/refunds и SaaS billing различаются.

Условные функции не исключаются молча: в матрице отмечены provider/feature gate,
API-only, legacy и будущая внешняя приёмка. Outreach/Market exchange и native-приложение
не становятся обязательной пилотной функцией из-за наличия папок/старого UI.
Существующие outreach API проверяются как отдельная совместимость без живой рассылки;
новый Market exchange и RN/device/store-приёмка не входят в этот web-прогон.

## Как будет выполняться «Компьютер»

Браузерные действия выполняются через plugin «Компьютер»: открытие страниц,
клики, клавиатура, file chooser, видимые диалоги и скриншоты. Не заменять их
Playwright, прямыми API-вызовами или присвоением состояния приложения через JS.
Существующие Playwright tests могут идти отдельным автоматизированным слоем.

Backend-readback и подготовка фикстур явно помечаются как технические действия.
Они доказывают сохранность, права и данные, но не прохождение UI. Если элемент
невозможно использовать через «Компьютер», фиксируется блокер/дефект, а не
незаметный обход. Реальная запись микрофона, нативный выбор файла и мобильное
устройство имеют отдельную границу: эмуляция viewport не подтверждает аппаратный
микрофон/камеру/touch. Недоступный инструменту шаг остаётся BLOCKED или выполняется
человеком с отдельным evidence, не объявляется автоматическим PASS.

## Автоматизированная часть: команды как план, не как результат

Текущий full runner проверен чтением исходника: он включает полный Django suite,
схему/system, frontend build/i18n/types/bundle, dependency checks и только mobile
owner/manager smoke. **`--mode full` не означает всю браузерную матрицу.**

После согласования candidate и реального ancestor base:

```powershell
.\.venv\Scripts\python.exe scripts\codex_verify.py --mode full --base-ref <approved-ancestor-base>
```

Base обязан быть предком и отличаться от HEAD; не подставлять случайный старый
коммит. При отсутствии committed range использовать документированный isolated
focused path и отдельно зафиксировать отсутствие range-gate. Точные команды
неизолированного `manage.py test`, `npm run e2e` на обычных8000/5173 сюда не включены:
текущий Playwright config может повторно использовать существующий сервер.

Дополнения к full: все выбранные Node policy/unit files из inventory, browser suites
по функциональной карте, PG-only/concurrency/constraint tests из inventory,
реальный Redis/Celery/AV/private storage и B-сценарии. Существующие специальные
Playwright configs/fixtures выбирать по test-файлу, не запускать весь каталог
в одном default config без проверки setup. Непокрытый матрицей пункт получает
явный ручной/API сценарий или gap, а не фиктивное имя существующего теста.

Для PG нужен отдельный isolated runner с disposable DB и explicit TEST.NAME;
DATABASE_URL обычной БД не допустим. Версии Python/Node и lock inputs проверяются
по testing guide; повторная локальная установка без изменения inputs не требуется,
в чистом CI deterministic install сохраняется. Подготовка недостающего harness
или новых автотестов является следующим согласуемым действием, сейчас кода нет.

## Результаты и условия приёмки

Каждая строка матрицы имеет статус `NOT RUN` до исполнения. Далее допускаются:
PASS, FAIL, BLOCKED (точная причина), SKIP (согласованное исключение, не PASS).
Варианты одной строки фиксируются отдельно; один удачный вариант не закрывает остальные.
Каждый result содержит run/candidate/env, role/effective scope, fixture IDs,
steps, expected/actual, screenshot/log/readback, defect ID, время и cleanup.

P0: утечка tenant/секретов, обход доступа, потеря/порча денег/данных, двойное
бронирование/списание. P1: основной процесс не завершается, ложный успех,
неправильный жизненный цикл, неработающее recovery. P2: некритичная ошибка
представления/эргономики; P3: косметика. Приоритет сценария и severity дефекта
фиксируются отдельно и не снижаются ради зелёного отчёта.

Общая функциональная приёмка: все включённые обязательные P0/P1 варианты PASS,
нет незакрытых P0/P1 дефектов; P2/P3 перечислены и приняты владельцем; coverage
по всем группам и маршрутам без скрытого NOT RUN. BLOCKED live/голос/миграция
не исчезает из общего заключения. Release readiness требует отдельного списка
AC/target/CI/операционных доказательств, не просто числа зелёных тестов.

Нагрузку проводить после функциональной части отдельным этапом. Предложение:
повторить прежнюю смесь запросов на малом/большом наборе с p95≤1с и errors<1%,
60с ступени и180с подтверждение, отдельно worker count/think time. Это пока
порог для обсуждения, не новое SLA. Зафиксировать RAM/CPU/paging/SQL; результаты
занятого локального компьютера не переносить на ёмкость выделенного сервера.

| Target | E1/E2 автоматически + отдельный E3 стенд с synthetic данными | Локальный E3 допустим, но нагрузочная оценка зависит от компьютера |
| Candidate | Один утверждённый снимок всех тестируемых изменений | При изменениях во время прогона отметить затронутые результаты и повторить их |
| Внешние эффекты | Сначала mocks/sandbox; live отдельным перечнем каналов/получателей | Нужны аккаунты, затраты и разрешённые операции для каждого provider |
| Дефекты | Сначала отчёт, без продуктовых исправлений | При разрешении fixes сохранять baseline и адресный retest на новом снимке |
| Ширина | Все группы матрицы; legacy/API-only отдельно от пилотной UI-приёмки | Исключения заранее перечислить, не заявлять после этого «проверено всё» |
| Human-assisted | Микрофон, screen reader, внешние MFA/доступы отмечать отдельно | Без участия пользователя соответствующие пункты могут остаться BLOCKED |

План можно согласовать целиком с выбранными исключениями. Сейчас не создавались
тестовые пользователи/данные, не запускались тесты/build/server/browser, не отправлялись
сообщения, не вызывались внешние модели и не изменялась БД.
